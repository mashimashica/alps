# プロセス記述の設計

## 目的

作業を実行する構成とは区別して、対象作業の目的と成功条件を、必要十分な境界と詳細を持ち理解・適用・評価が可能なプロセス記述、またはそのような記述に対する指摘を通じて明確にする。

## 成果

- 対象作業の目的と適用範囲、および隣接作業と重なる場合やその他の理由で境界が曖昧な場合の境界が、記述内で識別されているか、識別されていない事項を指摘が識別している。
- 記述の成果が、それぞれ目的の達成に必要で、全体として目的を満たすために十分な、観察可能な結果条件になっているか、満たされていない性質を指摘がそれぞれ識別している。
- 記述が、作業の理解・適用・評価に必要な詳細を含み、そのいずれにも寄与しない詳細を含んでいないか、不足または余分な詳細を指摘が識別している。
- 適用条件によって必要となる場合を除き、実行手段の選択が開かれているか、不要な固定を指摘が識別している。
- 依頼が変更を含む場合、その対象となる要素、範囲、根拠、影響、必要な再検証が識別されているか、識別されていない事項を指摘が識別している。
- 依頼がプロセスの選択やプロセスの意味の変更を含む場合、その選択が目的と適用条件に照らして正当化されているか、正当化されていない事項を指摘が識別している。
- フレームワークおよび必要な参照との記述の整合性が確立されているか、明示的な指摘によって限定されている。
- 未確認事項と適用上の限界が明示されている。

## 活動とタスク

以下のタスクは、推奨と明示したものを除き、依頼された範囲内で必須とする。それらの関係は、理解の進展に応じて記述を再検討することを支える。

### 対象作業の明確化

1. プロセスフレームワークと必要な参照の全文を読む。
2. 依頼範囲と、利用可能な記述または対象作業の情報を識別する。
3. 影響を受ける関係者からの必要な情報を用いて、作業が成立させることを引き受けた結果と、隣接作業との境界を明確にする。その責任を、便益や他の作業が担う結果と区別する。
4. その情報の出所と適用可能性を確認し、不足を識別する。不足が範囲や成功条件を変え得て、利用可能な情報から解消できない場合は、依頼者に確認する。
5. 意図した範囲や成功条件を変え得る不確実性を識別する。

### 成功条件と作業の記述

1. それぞれ目的の達成に必要で、全体として目的を満たすために十分な、観察可能な成果を記述する。独立して評価できる結果を区別可能に保つ。
2. 省くと理解・適用・評価が損なわれる詳細を含め、いずれにも寄与しない重複は削除または統合する。作業詳細が必要な場合は、関連する行為を有用な粒度の活動とタスクへ整理し、成果への寄与を確認する。
3. 必要な入力、出力、統制事項、制約、実行支援要素、開始基準、完了基準を、その機能に基づいて記述する。必須の方法と依存関係は適用範囲とともに維持し、それ以外の実行上の選択を開いておく。
4. Markdownではフレームワークの記述規則を適用する。対象がAgent Skillの場合は、本文にプロセス記述を、frontmatterに発見用の識別子と、作業およびその適用場面の要約を記述する。frontmatterとHost表示を、記述の意味と範囲に整合させる。

### 参照元と関係の整合

1. 参照元となる記述を識別し、必要な参照を意図した出典に照らして確認する。必要な資源の役割と利用条件を明確にし、参照資料と作業の記述を区別する。Skillでは、意図した配布構成の下でパッケージ内のリンクが解決し、外部参照が参照元を識別し、アクセス条件がある場合はそれも識別していることを確認する。
2. 関連する作業と共有する情報の意味、利用、変更影響を、どの作業が参照・更新するかを含めて明確にする。
3. 変更では、対象となる記述と要素、範囲、根拠、影響、必要な再検証を明確にする。意味の基準となる記述の変更、適用内容の文脈限定の変更、見せ方の変更を区別し、これらすべてを、記述が既に許容する文脈固有の選択と区別する。そのような選択は記述の変更に当たらない。
4. プロセスを選択する場合やその意味を変更する場合は、判断の裏付けに必要な証拠を用いて、提案された選択肢を目的と適用条件に照らして評価する。

### 記述の評価

1. フレームワークと適用される文脈上の要求に照らして記述を評価する。これには、要素の整合性、作業全体を記述する活動とサブプロセスがすべての成果を包含し目的に寄与しているか、選択した作業だけを記述するものがそれが支える成果を識別しているかを含む。基準と証拠が、レビュー対象の記述と文脈に適用できることを確認する。
2. 変化した情報や条件が根拠に影響する場合は、影響する基準、証拠、判断を再評価する。
3. 曖昧さ、裏付けのない成功条件、適用上の限界を明らかにできる場合は、影響、不確実性、複雑さに見合う労力で、代表的な事例を検討することが望ましい。反例を考える際は、目的、責任、範囲、適用条件を固定する。すべての成果が成立しても目的を果たしていない状況や、ある成果が成立しなくても目的を完全に果たせる状況はあるか。出力が存在し、または処理が成功しても、成果が成立しない状況はあるか。責任を変えたものは元の範囲内の反例ではなく、反例が見つからなくても、すべての事例での十分性を証明したことにはならない。
4. 指摘を用いて、依頼範囲内で必要なさらなる改訂やレビューを判断する。
5. 指摘を、その証拠と影響範囲とともに報告する。確認された未達成、証拠の不足、根拠のある適用外を区別する。裏付けられた結果と有用な途中作業を保持しつつ、それらを全体の成功と扱わない。レビューでは、提供された記述について本Skillの成果を評価する。指摘は未達成の条件を識別することで成果を限定するが、記述がその条件を満たすようにするものではない。

## 統制事項

意味とMarkdownの記述様式には[プロセスフレームワーク](process-framework.md)を適用する。対象がAgent Skillの場合、物理的な形式には[Agent Skills仕様](https://agentskills.io/specification)を適用する。これらは、それぞれの対象について必須参照である。

## 制約

変更は、ユーザーの依頼と利用環境の適用条件の範囲内にとどめなければならない。レビューだけの依頼には、指摘と依頼された修正を返し、求められていない変更を行ってはならない。作成や改訂では、指摘によって成果を限定してよいのは、依頼範囲、利用可能な情報、または権限の範囲内で満たせない条件に限る。対象の作業の実行や外部状態の変更には、適用される権限が必要である。未確認の参照や条件は、読んでいないフレームワークや必要な参照の内容を含め、それに依存する判断や行為を制限しなければならない。独立した作業は、それぞれの適用条件の範囲で続けてよい。
