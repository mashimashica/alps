## 1. 必須の中核だけで十分な作業

```markdown
---
name: identify-maximum
description: 与えられた空でない有限の整数集合から最大値を特定する。
---

# 最大値の特定

## 目的

与えられた空でない有限の整数集合における最大値を定める。

## 成果

- 特定した値が与えられた集合に属し、すべての要素以上である。
```

この結果条件は観察可能であり、限定された目的に十分である。目的が入力の範囲を示し、成果がアルゴリズムを指定せずにその最大値を識別する。空集合は明示した範囲外であり、暗黙に処理成功と報告してはならない。

## 2. 一度限りの文脈固有の作業

```markdown
---
name: relocate-october-workshop
description: A室の閉鎖に伴い、2026年10月8日の設計ワークショップの代替会場を整える。
---

# 10月ワークショップの会場変更

## 目的

A室の閉鎖後も2026年10月8日の設計ワークショップを開催できるようにする。

## 成果

- ワークショップの時間帯に代替室が確保されている。
- 代替室が、参加予定者全員の参加条件とアクセス上の必要を満たしている。
- 開催前に、参加予定者全員が代替会場を確認したと応答している。
```

日付と対象行事によって、必要な範囲を記述内で示している。会場の確保、適切さ、参加者の確認応答は独立して判断できる。招待の送信は出力であり、確認応答には相手からの返答が必要となる。アクセス上の必要が識別されていなければ未確認のままであり、会場の適切さの判断を制限する。

## 3. 固定成果物を必要としない作業

```markdown
---
name: clarify-outcome-and-output
description: 学習者が成功と成果物の作成を混同している場合に、成果と出力の区別を明確にする。
---

# 成果と出力の明確化

## 目的

学習者が作業の成功と成果物の作成を区別できるようにする。

## 成果

- 学習者が、説明で使用していない例において、結果条件と成果物を正しく区別している。
- 学習者が、成果物が存在していても意図した結果条件が未達成になり得る理由を説明している。
```

口頭のやり取りでも観察可能な証拠を得られる。文脈上必要でなければ、スライド、逐語録、固定の文書は不要である。説明を行ったことは、学習者の理解の証拠ではない。代表的な確認が支えるのは、観察した学習者と文脈に関する判断であり、永続的または普遍的な理解ではない。

## 4. 必要な承認、方法、順序

このサービスの本番運用方針は、候補版の適格性と本番での動作の確認を要求する。記述には、これらの義務を明確にする作業詳細と条件を追加する。

### 本番リリース

**目的：** 購入機能が動作する状態で、承認された変更を当該サービスの本番利用者が利用できるようにする。

**成果：**

- 承認された変更が本番で利用可能になっている。
- 本番のヘルスエンドポイントがreadyを返している。
- 利用者の購入経路でテスト購入が完了している。

**活動とタスク：**

- **候補版の適格性確認：** 候補版をサービスの受入基準に照らして検査しなければならない。その候補版そのものについて、サービス責任者の承認を得なければならない。
- **本番での利用可能性の確立：** 承認済み候補版を、サービスで認められたリリースジョブでデプロイしなければならない。本番の結果を受入基準に照らして検査しなければならない。

適格性確認は候補版を利用する根拠を成立させ、本番の作業はサービスの結果状態を成立させて確認する。両活動が成果に寄与し、タスクが個々の行為を述べる。候補版や本番の証拠が変われば、それぞれの活動を再び行える。

**統制事項：** このサービスの本番運用方針は、検査した候補版そのものへのサービス責任者の承認と、認められたリリースジョブの利用を要求する。受入基準は、ヘルスエンドポイントのready応答とテスト購入の完了を要求する。

**制約：** 候補版の検査は承認に、承認はデプロイに先行し、本番確認はデプロイ後に行わなければならない。候補版の変更により、先の検査と承認の根拠は無効となる。承認が不足または未確認の間は、デプロイしてはならない。

**開始基準：** 適格性確認のために候補版と受入基準が利用可能である。**完了基準：** 三つの成果すべての達成が本番の証拠で裏付けられ、適用されるリリース要件が満たされている。

**入力：** 候補版と変更要求。**出力：** デプロイされたサービスの版。**実行支援要素：** 検査能力と、認められたリリースジョブ。

方針は作業を方向付け、その承認条件はデプロイを制限する。リリースジョブは実行支援要素となる。開始基準は、デプロイの承認前に候補版の適格性確認を開始できるようにしている。デプロイの制約は、それが対象とする行為に引き続き適用される。

## 5. 複数プロセスが更新する共有情報

### 要件の明確化

**目的：** サービス変更のニーズを、解決案の選択に使える程度に明確にする。

**成果：** ニーズに観察可能な受入条件がある。重要な曖昧さや矛盾が解消されているか、解決案の選択への影響とともに識別されている。

### 実現可能性の評価

**目的：** 候補となる解決案が、利用可能な能力・容量の範囲内で明確化されたニーズを満たせるかを判断する。

**成果：** 検討した各候補の実現可能性が、ニーズと利用可能な能力・容量に照らした証拠で支えられている。未確認の仮定と、それが実現可能性の判断へ与える影響が明らかになっている。

両プロセスは、通常の一つの**変更概要**を参照・更新する。これには、このサービス変更のニーズ、候補に関する仮定、受入条件、裏付けとなる観察が含まれる。ニーズと観察は検討時の入力となり、受入条件は候補を判断する際の統制事項となる。更新した情報は出力である。同じ文書内でこれらの役割を区別できる。

| 作業 | 共有情報の利用 | 変更の影響 |
| --- | --- | --- |
| 要件の明確化 | 関係者の情報と実現可能性の評価結果から、ニーズと受入条件を具体化する。 | ニーズや受入条件の変更により、影響する実現可能性の判断を再検討する必要がある。 |
| 実現可能性の評価 | 能力・容量の証拠、候補の限界、現在のニーズへの問いを追加する。 | 新たな限界が判明すると、影響するニーズや解決案の選択を再検討する必要がある。 |

この共同作業では、参照者は利用した版を識別しなければならない。更新では確定したニーズ、提案、未確認の仮定を区別しなければならず、矛盾する知見を暗黙に上書きしてはならない。影響する作業が古い判断に依存する前に、変更情報を利用可能にしなければならない。保存と調整にはチームの既存の文書・版管理ツールを用いる。両プロセスは変更概要を繰り返し扱える。同じ水準での繰り返しの適用は反復であり、サービスとその構成要素にそれぞれ適用することは再帰である。統合では各水準内の完全性と水準間の整合性を確認する。サービス変更の利用可能な部分を成立させることは増分的適用である。検討する変更に応じ、これらの関係を組み合わせられる。

本番リリースの承認条件は、そのプロセスのデプロイに適用される。変更概要を共有することで、すべての明確化・評価作業の開始基準になるわけではない。

## 6. 横断的なビュー

**リリース判断ビュー**は、レビュアーに関係する出典要素へのリンクを提示する。

| 関心 | 出典 | 確認する事項 |
| --- | --- | --- |
| ニーズの適切さ | [要件の明確化](#要件の明確化) | 受入条件と未解決の曖昧さ。 |
| 解決案の裏付け | [実現可能性の評価](#実現可能性の評価) | 候補の実現可能性の証拠と限界。 |
| 本番へ影響を与える許可 | [本番リリース](#本番リリース) | 適用範囲が明確な承認と順序の条件。 |

ビューは出典の記述へのアクセスを提供し、リリース判断との関係を説明する。目的と成果は出典の記述に保持する。レビュアーは第二の承認者を、提案と明示して提案してよい。その表示によって出典の方針が変わったりリリースが許可されたりすることはない。適用する方針や記述の変更は、その権限と範囲に従って扱わなければならない。

## 7. 参照不足のレビュー

草案がリリース承認の基準として`service-policy.md`のrevision 7を要求しているが、revision 6しか利用できないとする。これらは架空の識別情報であり、同梱ファイルではない。

例えば次のように報告できる。「必要なrevision 7が提供されていない。承認権限とリリース条件は未確認である。利用可能なフレームワークに照らして草案の目的と成果の表現はレビューしたが、方針との整合性は判断できない。このレビューをデプロイ承認として用いることはできない。この評価部分を完了するには、意図した版の提供が必要である。」

revision 6や同名の方針で代用しない。不足していることを理由に方針を適用外にしない。レビューだけの依頼には指摘と影響を返し、草案を暗黙に書き換えたり、不足する承認条件を創作したりしない。

## 8. 出力はあるが成果は未達成

[本番リリース](#本番リリース)において、リリースジョブがデプロイログを生成し、意図した版がデプロイされたとする。本番ヘルスエンドポイントはreadyを返すが、テスト購入は失敗する。承認の証拠は提供されていない。

デプロイされた版とログは出力である。結果条件を個別に評価する。

| 条件 | 証拠と判断 |
| --- | --- |
| 承認された変更が本番で利用可能になっている。 | 意図した版は存在するが、承認済みかどうかは未確認である。 |
| 本番のヘルスエンドポイントがreadyを返している。 | 観察結果が、この成果の達成を裏付ける。 |
| 利用者の購入経路でテスト購入が完了している。 | 購入の失敗が、この成果の未達成を示す。 |
| 承認要件が満たされている。 | 承認の証拠が不足しており、充足は未確認のままである。 |

リリースの完了基準は満たされていない。事実は、購入失敗の報告と不足する承認証拠の要求を支える。承認があったとも、なかったとも断定する根拠にはならず、既存の出力とヘルス確認の成功によって全体の成功が成立することもない。
