# プロセス記述を設計する

## 目的

プロセススキルの正本となるプロセス記述を、その意味、成功条件および再利用可能な境界が明確になるために必要な最小限の詳細で設計または再設計する。

## 成果

- 反復される作業が、一つの一貫したプロセス境界として説明されている。
- 名称、目的および観察可能な成果が、特定の実行者、ツール、方法または順序に依存せず成功を示している。
- 再利用可能なプロセス知識と、一回の適用に固有の情報が区別されている。
- 正確性、安全性、意味、組合せ可能性または評価可能性に必要な詳細だけが残っている。
- 既存スキルの改訂では、利用証拠ならびに未解決の仮定および限界が記述へ反映されている。

## 行う作業

1. 反復される作業、その対象、意図する利用状況および過去の利用から得られる証拠を確認する。
2. 明確な名称を選び、一つの目的と、その目的を満たすために十分な観察可能な成果を定める。
3. 継続的に使えるプロセス知識を、案件固有の目標、値、人、ツール、ファイル、リポジトリおよび実行文脈から分ける。
4. 正確性、安全性、意味、組合せ可能性または評価可能性の観点から必要性を説明できない詳細は追加しない。
5. 活動、タスク、入力、出力、条件または受け渡しは、それらがなければプロセスが曖昧または利用不能になる場合にだけ追加する。
6. 不要な実行者、ツール、方法、指標、ファイルパス、リポジトリ詳細、固定順序および特殊事例分岐を削除する。
7. 代表事例または利用証拠に照らして記述を確認し、不明確、重複、効果不足または負担となる内容を改訂する。
8. 作成または改訂したプロセス記述とともに、未解決事項、明示した仮定および既知の限界を提示する。不明点を推測で補わない。

新規作成と改訂は、最善の現行プロセス記述を設計するという同じ責務である。別々のライフサイクル手順を導入しない。

## 境界

- 対象プロセススキルの通常の成果を達成するために、そのプロセスを実行しない。
- 常設の仲介としてスキルを選定せず、複数スキルを実行統括しない。
- Git、リポジトリ、ブランチ、コミット、リリース、版、公開、状態、採用または廃止を管理しない。
- 形式的な適合、能力、成熟度または認証を主張しない。
- 表現モデル、パッケージ識別、解決機構、専用記録、スキーマ、パーサー、検証器、CLI、生成器またはホストの意味論を作らない。
- 既定ですべての参考資料を読まない。
- より小さな記述で十分な場合に完全なテンプレートを必須としない。

利用者が対象プロセスの成果を必要とする場合は、対象スキルを直接適用する。このスキルは、対象スキルのプロセス記述を作成、改訂または簡素化するときだけ使用する。

## 必要な場合だけ参考資料を読む

- 目的に複数の独立した意図が混在する、成果が成果物や手順として書かれている、成功を評価できない、または隣接スキルと目的が重なる場合は、[目的と成果](purpose-and-outcomes.md)を読む。
- スキルが一案件向けに細か過ぎる、複数の目的を持つ、手順書になっている、分割か統合かで迷う、役割・ツール・順序を固定する必要性が不明である、または利用証拠から何を削除すべきか迷う場合は、[境界と詳細](boundary-and-detail.md)を読む。
- エージェントやツールが入力とされている、成果と出力が混同されている、規則・制限・資源の区別が不明である、開始または完了条件が曖昧である、またはスキル間の受け渡しで意味が失われる場合は、[入力、出力および条件](inputs-outputs-and-conditions.md)を読む。

該当する条件の参考資料だけを読む。各参考資料は単独で利用できる。
