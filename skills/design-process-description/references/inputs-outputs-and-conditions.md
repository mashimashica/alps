# Inputs, Outputs, and Conditions

Use this reference to answer: **What function does each item or condition around the Process serve?**

Add these distinctions only when they clarify the Process, its conditions, or a Handoff. Do not create empty categories.

## Functional Distinctions

| Kind | Function | Diagnostic question |
| --- | --- | --- |
| Input | Information, material, or state the Process consumes or transforms | What enters the work and is used to produce a result? |
| Output | Information, material, or state produced by the Process | What leaves the Process as a result of the work? |
| Control | A rule or direction that governs decisions or acceptable work | What directs how choices are made or results are accepted? |
| Constraint | A limit the Process must not exceed or violate | What bounds the available choices? |
| Enabler | A resource or capability that makes execution possible | What helps perform the work without being transformed as its subject? |
| Entry Criterion | A testable condition that must hold before the Process starts | What must already be true for starting to be valid or meaningful? |
| Exit Criterion | A testable condition that must hold before the Process is considered complete | What must be true before stopping is permissible? |

People, agents, tools, systems, and environments are normally Enablers, not Inputs. A rule can arrive in a file without becoming an Input in function; classify the rule as a Control or Constraint according to what it does.

The same real-world item may serve different functions in different Processes. Classify it by its function at this boundary, not by its file type or label elsewhere.

## Controls, Constraints, and Enablers

- Use **Control** for policy, criteria, or direction that shapes decisions or evaluation.
- Use **Constraint** for a non-negotiable boundary such as a time, permission, compatibility, legal, or safety limit.
- Use **Enabler** for access, expertise, tools, infrastructure, or other capabilities used to perform the work.

Do not list every available resource. Include one only when its function is necessary to understand, perform, compose, or assess the Process.

## Connect Outcomes and Outputs

An Outcome is a successful state; an Output is something produced. Connect them by stating how an Output supports or evidences an Outcome when that relationship is not obvious.

For example, a risk register may be an Output. “Material risks and their treatment are visible to the decision maker” may be an Outcome. The register supports the Outcome only if it contains the relevant information and reaches the decision context; mere file creation is insufficient.

Avoid turning every Outcome into a required document. Evidence may be a changed state, an observation, a message, or another suitable result.

## Entry and Exit Criteria

Use criteria as predicates, not events or Tasks.

- Weak: “Receive the request.”
- Stronger Entry Criterion: “The requested decision and its scope are identifiable.”
- Weak: “Send the report.”
- Stronger Exit Criterion: “The intended recipient can access the result and its material limitations.”

Add criteria only when they settle a meaningful ambiguity not already resolved by Inputs, Outcomes, or Constraints.

## Handoffs Between Skills

Describe a Handoff when one Process's Output is intended to become another Process's Input and meaning could otherwise be lost.

State only what is needed:

1. the provider Output;
2. the recipient Input;
3. the meaning or condition that must be preserved; and
4. any acceptance condition needed by the recipient.

Do not prescribe a transport, file format, repository path, or orchestrator unless it is essential. Do not add a permanent registry merely to record the mapping.

## Result

Retain only the functional distinctions that remove ambiguity. Ensure required Inputs and conditions support the work, Outputs connect to Outcomes, and any necessary Handoff preserves meaning across the boundary.
