# Purpose and Outcomes

Use this reference to answer: **Why does this Process exist, and what state shows that it has succeeded?**

## Name

Give the Process a short noun phrase that identifies the recurring work without naming a temporary project, performer, tool, or implementation. The Name should distinguish the Process from neighboring Skills while remaining true across its intended applications.

## Purpose

The Purpose is the single reason the Process exists. State the valuable condition the Process is intended to establish, not the steps used to establish it.

A useful Purpose:

- describes one independent intent;
- stays meaningful across representative applications;
- does not prescribe a performer, tool, method, artifact format, or sequence; and
- is specific enough to exclude work that belongs to a neighboring Process.

If a sentence joins independent intents that could succeed or fail separately, either choose the dominant intent and move supporting work inside its boundary, or split the work into separate Processes. Do not keep several independent purposes merely because they often occur together.

## Outcomes

Outcomes are observable or assessable states that must hold for the Purpose to be satisfied. Write each Outcome as a condition that can be examined, not as an instruction.

Prefer statements such as:

- “The affected decision is supported by current, relevant evidence.”
- “Material uncertainty and its effect on the result are visible.”

Avoid statements such as:

- “Create a report.” This is an Output.
- “Review the sources.” This is a Task.
- “Improve quality.” This is a benefit without an assessable success state.
- “Use tool X.” This is an implementation choice.

## Outcome, Output, Task, and Benefit

| Item | Question it answers | Example |
| --- | --- | --- |
| Outcome | What state shows success? | Relevant uncertainty is visible to the decision maker. |
| Output | What does the Process produce? | A decision brief. |
| Task | What work may be performed? | Compare the evidence. |
| Benefit | Why might success matter beyond the Process? | Fewer avoidable reversals. |

An Output can provide evidence for an Outcome, but producing an artifact does not by itself establish success. A Task can contribute to an Outcome, but completing the Task does not prove the resulting state. A benefit may motivate the Purpose, but it is not an Outcome when the Process cannot reasonably establish or assess it.

## Check Sufficiency and Relevance

Test the Purpose and Outcome set together:

1. **Coverage:** If every Outcome holds, is the Purpose satisfied?
2. **Necessity:** Does each Outcome contribute to the Purpose rather than describe optional quality or a neighboring intent?
3. **Observability:** What evidence or observation could distinguish achievement from non-achievement?
4. **Independence from implementation:** Could different capable performers and methods achieve the same Outcomes?
5. **Coherence:** Do the Outcomes describe success for one Process rather than several loosely related Processes?

Add an Outcome only to close a real gap in coverage. Remove or narrow one that is redundant, unassessable, outside the Process's influence, or merely restates an Output or Task.

## Result

Produce a stable Name, one Purpose statement, and the smallest Outcome set that is sufficient, relevant, and assessable. Record any unresolved assumption that prevents a success condition from being stated confidently.
