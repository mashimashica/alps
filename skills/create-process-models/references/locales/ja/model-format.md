# プロセスモデルのPlugin形式

[英語版](../../model-format.md)

一つのプロセスモデルを一つのAgent Pluginとする。本リファレンスはALPSモデルプロファイルの第1版を定める。プロセス記述をパッケージ化するものであり、すべてのSkillをモデルの構成員にするものではない。このプロファイルは本Skillが作成するモデルパッケージに適用し、すべてのALPSプロセス記述に必須要素を追加するものではない。

## 正本

| 正本 | 保持する内容 |
| --- | --- |
| `plugin.json` | パッケージの識別、リリース版、明示的なモデル構成員。 |
| 列挙されたプロセスのMarkdown文書 | 表示名、目的、成果、必要な詳細、入出力の宣言。 |
| `references/artifacts/<id>.md` | 共有する情報項目・製品・サービス一つの定義。 |
| 任意のワークスペース設定`alps-harness.yaml` | 具体的な成果物の配置と実行設定。 |

グラフはこれらの正本から導出する。別のモデルファイル、型レジストリ、エッジ一覧、目的や成果の永続的な複製は置かない。モデルは循環を含みうる。入出力は、実行順序、必須の利用可能性、開始許可、承認、成果の達成を定めない。

## Manifest

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "service-change",
  "version": "0.1.0",
  "extensions": {
    "io.github.mashimashica.alps": {
      "version": 1,
      "processes": ["./skills/implement-change/SKILL.md"]
    }
  }
}
```

この拡張がプロファイルを識別する。拡張内の`version`はモデル形式の版であり、ルートの`version`は指定する場合にパッケージのリリース版を表す。どちらもプロセスや成果物の定義には繰り返さない。拡張内の任意の`title`は、日本語の名称などの表示名を与える。別の識別子ではない。

`processes`は各構成文書を一度ずつ列挙する。並び順は実行順序ではない。空の配列は草案フラグを加えずに空のモデルを表すが、実質的な仕事を記述する依頼を満たすものではない。補助SkillはHostが発見するだけではモデルの構成員にならない。

Skillは`./skills/<name>/SKILL.md`に置く。それ以外の仕事には、`./processes/review-change.md`など通常のMarkdownを使える。人の仕事のために架空のSkillを作る必要はない。解決後のsymlinkも含め、パッケージ内のファイルパスはすべてPluginルート内に収まらなければならない。可搬manifestとSkillの形式は[Agent Plugins](https://agent-plugins.org/specification)と[Agent Skills](https://agentskills.io/specification)に従う。Hostアダプターは依頼された利用先が必要とする場合にだけ用い、別のモデル定義を追加しない。

## プロセス文書

`skills/implement-change/SKILL.md`の例：

```markdown
---
name: implement-change
description: 合意した設計を実装する際に、検証可能なリリース候補を準備する。
metadata:
  inputs: '["design-description"]'
  outputs: '["release-candidate"]'
---

# 変更の実装

## 目的

十分な情報に基づくリリース判断のため、合意したサービス変更を利用可能にする。

## 成果

- 候補が、定められた範囲内で合意した設計を実現している。
- 関係する検証結果と未解決の制限を、リリース判断に利用できる。
```

本文にはH1の名称、`## Purpose`、リスト形式の`## Outcomes`を置く。日本語の文書では`## 目的`と`## 成果`を使える。成果は観察可能な成功条件であり、出力の存在だけでは達成を確認できない。その他の詳細は、仕事の理解・適用・評価に必要な場合に加える。メタデータに目的や成果を重複させない。

Skillの`name`を安定したプロセス識別子とし、ディレクトリ名と一致させる。通常のプロセス文書は`.md`を除いたファイル名を識別子とし、Skill発見用フィールドを持たずに同じ`metadata`を利用できる。プロセス識別子はAgent Skillの名前構文に従い、ASCIIの小文字英数字と単独のハイフンを用い、64文字以内で、先頭・末尾にハイフンを置かない。モデル内で一意とする。表示名はH1に置き、識別子とは独立に変更できる。

Agent Skillsのメタデータは文字列から文字列へのマッピングである。`inputs`または`outputs`を置く場合、その値は重複のない型識別子のJSON配列を文字列として格納しなければならない。省略したフィールドは、その役割の関係を宣言していないことを意味する。`alps.`接頭辞、重複する`id`、文書ごとのスキーマ版、統制事項という役割は置かない。仕事が同じ型を利用・更新する場合は、両方の役割に現れてよい。利用を規定する条件は本文に置き、別の入出力一覧を維持しない。

## 共有定義

参照するすべての型に定義が必要である。`release-candidate`は`references/artifacts/release-candidate.md`を直接参照する。

```markdown
---
kind: product
---

# リリース候補

検査とリリースに提出する改訂。版またはダイジェストにより一意に識別できる。
```

例の入力には`references/artifacts/design-description.md`も必要である。

```markdown
# 設計記述

実装と検証に用いる、合意した変更の範囲、意図した振る舞い、適用される制約。改訂と合意状態を識別できなければならない。
```

ファイル名を識別子、H1を表示名、残りの本文を意味と必要な特性の定義とする。型識別子にはUnicodeの文字と数、ドット、アンダースコア、ハイフンを使い、先頭は文字または数とし、パス区切りを含めない。参照は表示文ではなく識別子に完全一致させる。定義の欠落はエラーであり、読み手が型を捏造してはならない。

必要な場合の`kind`は`information`、`product`、`service`のいずれかとする。仕事に必要なら、詳細な節や機械可読スキーマへのリンクを含められる。スキーマも別の`INTERFACE.md`も必須ではない。参照された定義がモデルの成果物型を構成し、manifestのレジストリに重複させない。

## ワークスペースと編集

ワークスペース自体にPluginを置ける。別の場所にある場合は、`alps-harness.yaml`の`model`から、ワークスペースを基準とする相対パスでその`plugin.json`を指す。manifestがワークスペースのルートにあれば`model`を省略する。例：

```yaml
language: ja
artifacts:
  release-candidate:
    paths: ["releases/*/candidate.json"]
```

ワークスペースは型識別子を具体的なパスに対応づける。型の意味や種別の上書き、プロセスと別Skillとの対応づけ、Skill探索ルートの追加は行わない。エージェント設定、ガイダンス、スケジュール、添付はワークスペースが扱う。実行記録はモデル定義でもPlugin配布物でもない。

編集では、列挙されたMarkdownの正本とmanifestの構成員を更新する。無関係な文章を保全し、識別子・型・構成員を変える際は影響する参照を確認する。提供前にパッケージをレビューし、検証する。`process-model.yaml`、代替のモデル拡張、Skill名による推測、重複する入出力の正本は、このプロファイルに含めない。移行が依頼された場合は、正本を明示的に変更し、既存の記録と参照への影響を扱う。読み込みで旧形式へフォールバックしない。
