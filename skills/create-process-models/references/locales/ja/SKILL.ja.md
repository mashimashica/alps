# プロセスモデルの作成

## 目的

一つのPluginの原文書を通じて、プロセスの責務、成功条件、共有する情報を理解・維持できる、関連する仕事の実用的なモデルを確立する。

## 成果

- 選択したプロセスの網羅性と境界が、意図した仕事と適用条件に照らして正当化されている。
- 各プロセスに、観察可能な成功条件を持つ一貫した原記述がある。
- 共有する情報と成果物の関係に、曖昧さのない定義と参照がある。
- モデルが、依頼された配布形態において自己完結したPluginとして利用できる。
- 前提、未解決事項、検証の限界が明示されている。

## 活動とタスク

以下のタスクは依頼の範囲内で必須とする。関係や証拠から不足が明らかになった場合は、それまでの判断を見直す。

### モデルの範囲設定

1. モデルの目的、適用文脈、想定利用者、利用できる原記述、依頼された利用先を特定する。モデルの作成と、記述する仕事の実行を区別する。重要な不足は利用できる情報源から解消する。範囲や成功条件を変える不足が他の方法では解消できない場合は依頼者に確認する。
2. 一貫した責務と意図する結果によってプロセスの境界を選ぶ。依頼された仕事を網羅するのに必要なプロセスを選び、工程の捏造、ツール呼び出しごとのプロセス化、担当者が変わるという理由だけでの分割は行わない。モデルの対象外とその理由を明示する。
3. 各プロセスに名称、目的、一つ以上の観察可能な成果を定める。各成果は目的に必要であり、定めた範囲内で、それらが揃えば目的に十分でなければならない。出力の存在だけを成功条件にしない。活動、タスク、制約、実行支援要素、開始・完了基準は、理解・適用・評価に影響する場合にだけ加える。適用される義務とその出典を維持する。

### 関係の定義

1. 各プロセスが利用・生成する情報項目、製品、サービスを特定する。意味が同じものには一つの共有定義を用いる。名前が似ているだけでは同一性を確立できない。必要な範囲、特性、利用条件、変更の影響を定義または関係するプロセスに示す。
2. 利用するものを入力、生成・更新するものを出力として宣言する。仕事で用いる基準や方針も入力とし、記述の中で規範強度と範囲を維持する。同じ型を入力と出力の両方にできる。型の定義を、具体的なファイルやインスタンスと区別する。
3. 共有する型識別子を通じて各受け渡しを追跡する。外部から供給される入力と外部で利用される出力を明らかにする。根拠のある循環と共有情報の反復利用を維持する。入出力の関係や文書の並び順は、権限を与えず、準備完了を定めず、実行順序を指定しない。必要な承認や順序は仕事の条件として明示しなければならない。

### Pluginの作成

1. [モデル形式](model-format.md)を読み、一つのモデルを一つのPluginとして作成する。定められた正本と識別子の規則を用い、別のモデルファイル、型レジストリ、入出力一覧を追加しない。
2. Agent Skillとして提供する仕事は`skills/<name>/SKILL.md`に置く。人の仕事など、それ以外の仕事には通常のプロセスMarkdownを用いる。ノードを描くためだけに実行可能なSkillを捏造しない。モデルの構成員は`plugin.json`に明示的に列挙する。補助Skillは自動的に構成員にならない。
3. 共有定義は`references/artifacts/`に置く。記述する仕事に必要な場合にだけ、補助資料、スクリプト、スキーマを含める。再利用する意味はPluginに置き、具体的な成果物パスや実行設定との対応づけは、依頼された場合にワークスペース設定で行う。
4. 提供された原文のうち変更対象外の文章を保全する。既存パッケージでは安定した識別子を維持し、変更前に参照を調べ、意図した変更とその影響を明示する。旧形式の移行は依頼された場合に明示的に行い、互換読み込みや正本の重複は残さない。

### モデルの検証

1. 配布される形でパッケージを調べる。manifestの構成員、Skillのfrontmatter、プロセス記述、文字列化した入出力配列、共有定義、識別子の一意性、相対リンク、解決後のパッケージ境界を確認する。すべての入出力参照が定義へ解決しなければならない。定義がなければ、意味を捏造せず欠落を報告する。
2. 元の仕事に照らして網羅性と境界の選択をレビューする。循環、外部入力、共有方針があればそれらも含め、代表的な入出力関係を追跡する。すべての成果が成立してもプロセスの目的が達成されない場合や、出力が存在しても成果が未確認のままとなる場合がないかを調べる。
3. 適用できるローダーや検証器が利用できる場合は、パッケージを読み込み、意図した構成員と関係が保たれることを確認する。使用したツールと版を明示する。形式検証、意味のレビュー、実際の実行証拠を区別する。グラフの表示は、モデル化した仕事の成功を証明しない。
4. パッケージの場所、範囲と出典、検証証拠、未解決事項を提供する。原文や共有定義が変わった場合に再検証が必要な判断を明示する。

## 入力

ユーザーが意図する仕事、適用される要求、利用できる原記述がモデルの意味を規定する。[モデル形式](model-format.md)が正本の形式を規定する。本Skillはモデル作成に必要な案内を内包し、別のSkillがインストールされていることを要求しない。

## 制約

変更は依頼の範囲と権限内に収めなければならない。モデルの作成は、そのプロセスの実行、Hostへのインストール、公開を許可するものではない。未確認情報や未読の必須資料は、それらに依存する判断や主張を制限しなければならない。独立した作業は適用条件の範囲内で続けられる。有用な部分成果を保全し、未達の成果を明示して、不完全なモデルを完成済みとして扱わない。適用要件が制約する場合を除き、実行方法の選択肢を残す。
