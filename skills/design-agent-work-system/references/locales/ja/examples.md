# 設計の問いと具体例

[英語版](../../examples.md)

本資料は[エージェント作業システムの設計](SKILL.ja.md)のための参考情報である。依頼された設計に必要な詳細を選ぶ。構成は対象Skillと既存の資源に記述でき、以下の問いは別文書の作成を要求しない。

## 仕事の記述から始める

設計は、Skill、チケット、手順書、ユーザーの依頼など、形式を問わない対象の仕事の記述から始まる。仕事の意味と成功条件はその記述を参照し、必要な責務と相互作用を説明する。構成に必要な意味や条件が欠けている場合は、それを補わず、不足として報告する。構成の利用・実現・評価に必要な詳細だけを加える。

有用な問いには、次がある。仕事と条件はどの参照元に記述されているか。各責務をどの能力が担うか。文脈に応じた判断はどこに必要か。各インターフェースをどの情報が通るか。仕事の結果をどの証拠が支えるか。何が未確認か。

## 既存ツールと新しい組合せ

リポジトリ保守では、既存の検索ツールが候補ファイルを探し、既存のコンパイラが変更を検査する。エージェントは依頼された動作を解釈し、対象コードを選ぶ。生成ファイルに対する既定の一連の検査は、既存の一つのビルドコマンドで公開できる。内部の検査は個別に保守でき、エージェントはその操作を適用する場面を選ぶ。ビルドコマンドが必要な動作と診断を提供するなら、追加スクリプトは不要である。

## 同梱する処理ツール

基準と候補のリクエスト測定値を比較し、サービス変更が指定された試行に適しているかを評価する仕事を考える。その対象Skillは、両CSVファイルを検証し、各ファイルのnearest-rank p95応答時間とエラー比率、基準に対する候補のp95増加を計算し、両ファイルが同じリクエスト識別子の集合を含むかを報告し、引数で渡した限度値と結果を比較するスクリプトを同梱する。これらの計算を一つの公開操作とする。エージェントは、適用する測定の組と基準を選び、比較可能性を評価し、証拠を解釈し、追加測定の必要性を判断する。仕事の目的と成功条件は仕事の記述に保持し、実現を支える設計ではそれらを参照する。

## 能力・基準・制限

その試行で肯定的な評価をするには、各ファイルに4件以上のリクエストがあり、候補p95が200 ms以下、候補エラー比率が0.05以下、候補のp95増加が50 ms以下であり、いずれも記述された同じ条件で測定されている必要がある。同じ測定操作が、仕事に対して複数の関係を持つ。

| 側面 | 仕事との関係 | 設計と評価への関係 |
| --- | --- | --- |
| 測定値の読取り、指標の計算、値の比較 | 能力：スクリプトがこの処理を行う。 | 能力が定められた動作を実現しているか確認する。 |
| 試行の指標定義と受入限度値 | 基準：仕事がそれらを定め、スクリプトがその計算と比較を実装する。 | 実装した基準を、それらを定める試行条件へ、その参照元と範囲を含めて対応付ける。 |
| 必須のCSV文字コードと列 | インターフェースの制限：このツールの利用を制限する。 | 利用可能な情報を、その意味を変えずにインターフェースへ供給できるか確認する。 |
| 返された測定値と比較結果 | 証拠：評価を裏付ける。 | 測定文脈と適用基準を合わせて解釈する。リクエスト識別子が一致するだけでは、両ファイルが同じ固定リクエストセットを測定したとは確認できない。 |

ツールの能力と、基準の実装は、異なる関係である。規則は、その意味と適用範囲を識別できれば、設定やコードで表現できる。このツールは受入限度値を明示的な引数として受け取る。基準を固定したツールでは、その基準の根拠と適用可能性を識別する必要がある。閾値の変更は判断基準に影響し、受け入れる情報と動作を変えないCSV解析の変更は、実装の変更になり得る。

利用できるAPIが1ページにつき最大1,000件を返す場合、その上限は呼出しに適用される。全件を評価する仕事の要求には、ページ取得の反復や他の十分な能力を用い、全件を対象とする必要がある。最初のページの証拠が裏付けるのは、そのページの結果に限られる。上限があることから、残りの記録が評価対象外とは判断できない。

## 状態を変更するツール

カレンダーAPIは、その保証が仕事の要求を満たす場合、予定の競合検出と作成を一つの操作にまとめられる。その場合も、誰がどの予定を作成できるか、どの状態が変わり得るか、同時変更が結果へどう影響するかを定める必要がある。作成が行われた可能性のある要求がタイムアウトした場合、対応する要求識別子と状態照会によって、再試行前に影響を確認できる。そうした能力が利用できない場合、状態を確認するまで結果は不確かであり、エージェントはタイムアウトから「何も起きなかった」と推測してはならない。

## 能力の変化

モデル更新後の設計レビューで、ツール選定の弱さを補う指示が不要と分かる場合がある。影響する仕事で、より簡潔な相互作用を評価する。どの記録を変更してよいかを定める業務基準と、実際の影響の証拠は維持する。プロンプトが短いことや呼出し回数が少ないことだけでは、改善は確認できない。

上記のサービス評価への変更は、証拠の異なる部分に影響し得る。その測定は同時クライアント数1で行われ、候補の測定p95は160 msである。

| 仮の変更 | 設計上の対応と証拠の範囲 |
| --- | --- |
| 代替CLIが、計算とその意味を保ちつつ、同じ測定値と限度値を名称変更した引数で受け取る。 | 呼出し方を調整し、影響するインターフェースとエージェントの解釈を確認する。適用可能な測定証拠は引き続き利用できる。インターフェースの変更だけで、新たなサービス測定が必要になるわけではない。 |
| 権限に基づく試行条件の改訂で、候補のp95上限を200 msから150 msへ変え、測定条件は変えない。 | 変更された基準とその範囲を識別する。適用可能なp95測定値160 msを保持し、150 msに照らして再評価すると、候補はこの基準を満たさない。引き続き適用できる他の指摘の裏付けは保持される。正確な不適合評価は、候補を適切な状態にしなくても、評価業務の成功になり得る。 |
| 意図する試行を同時クライアント数1から10へ変える。 | クライアント数1の証拠の比較可能性と適用可能性を再検討する。影響する判断の根拠を得る。以前の測定値で計算が成功しても、クライアント数10での適切さを主張しない。以前の証拠は、実際に対象とした条件について保持する。 |

二つ目と三つ目の変更は仕事の適用条件に関わり、仕事の記述の変更権限に従う。ツールに合わせて成功条件を黙って定義し直す理由にも、影響しない検査を繰り返す理由にもならない。
