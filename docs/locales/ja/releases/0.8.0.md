# ALPS 0.8.0

[English source](../../../releases/0.8.0.md)

ALPS 0.8.0では、2つの設計Skillをそれぞれ単独で利用できる構成にし、成功条件とレビューの境界を明確にしました。また、要求・権限の尊重を、ツールの振る舞いやワークシステムの有効性とは分けて評価します。

## 単独で利用できる設計Skill

[design-process-description](../../../../skills/design-process-description/references/locales/ja/SKILL.ja.md)と[design-agent-work-system](../../../../skills/design-agent-work-system/references/locales/ja/SKILL.ja.md)は、それぞれに必要な原則と補助リソースを自身のディレクトリに収録しています。相対リンクは各Skillのディレクトリ内で解決し、他方のSkillやリポジトリの`examples/`には依存しません。組み合わせて使う場合は、仕事の記述を受け渡します。

設計責任の区別は維持しています。Process Description Designは、仕事が何を達成すべきかを明確にします。Agent Work System Designは、依頼を含む任意の形式の仕事の記述を受け取り、不足している仕事の意味を補って定義することなく、その実現構成を設計します。

## 成功条件とレビューの境界

[Process Framework](../../../../skills/design-process-description/references/locales/ja/process-framework.md)では、規範的な強さと網羅性を明確にしました。仕事全体を記述するActivityやSub-processは、すべてのOutcomeを網羅し、Purposeに寄与します。一部の仕事を記述する場合は、どのOutcomeを支えるかを示します。未確認の事実、仮定、未達の条件、除外は、成功とは区別して扱います。

両設計SkillのOutcomesは、作成・改訂・レビューのいずれにも適用できるようにしました。成立していない条件は指摘事項として示します。作成・改訂で指摘事項によりOutcomeの成立を限定できるのは、定められた範囲、情報、権限、またはワークシステム設計の場合は利用可能な能力の範囲内で、その条件を満たせないときに限ります。成功条件を弱めたり、未確認の条件を達成済みとして扱ったりすることを認めるものではありません。レビューのみの依頼は、求められていない変更を行う権限を与えません。

Process Description Skillでは、責任境界、Outcomeに対する反例、変更の識別と正当化、参照資料を読んでいない場合の判断の限界、前提が変わった場合の再評価も明確にしました。例とテンプレートも、これらの区別に合わせて更新しています。

## 要求・権限と評価

[エージェントワークシステムの設計原則](../../../../skills/design-agent-work-system/references/locales/ja/agent-work-system-design.md)と対応するSkillでは、権限、情報の信頼性、費用と待ち時間、最小限のアクセス、および信頼できない情報を指示や許可ではなくデータとして扱うことを取り上げています。

ワークシステムの評価では、設計の整合性、構成要素と接続の振る舞い、適用される要求・権限・影響範囲の制限の尊重、代表的な仕事を通じた有効性を区別します。Skillとリポジトリのガイダンスでもこれらの判断を分け、変更した構成を再び信頼して利用する前に再評価が必要となる条件を扱っています。

## 実例・配布・リポジトリのガイダンス

[サービス変更評価の実例](../../../../examples/locales/ja/README.md)では、Python 3.10以降が必要です。ツールは、曖昧なリクエスト識別子、未対応の数値形式、UTF-8 BOM付き入力を拒否し、バイト列の一致とリクエスト識別子の一致を`input_relationship`として出力します。識別子の一致は測定結果の比較可能性を判断するための証拠ですが、それだけで文脈上の比較可能性が確立するわけではありません。評価ケースには、パイロットを合格させるために受入基準を緩める依頼を含め、基準の変更には権限が必要であることを示しています。

配布構成の検査では、いずれの配布Skillについてもディレクトリ外へ出るリンクを拒否します。日本語のSkill本文は、重複検出を避けるため`SKILL.md`から`SKILL.ja.md`に変更しました。翻訳manifestには、各翻訳の英語原文とレビュー済み原文のSHA-256を記録します。検査が検出するのは再レビューの記録を伴わない原文の変更であり、検査だけで意味の同等性を確認するものではありません。

このリリースでは、Claude CodeのMarketplace manifestと導入手順も追加しました。Pluginの版番号はPlugin manifestで管理し、Marketplaceの項目には重複させません。リポジトリ開発用の`CLAUDE.md`も追加しています。README、Plugin、ソーシャルプレビューの説明は、仕事の意味とその実現構成の設計というメッセージに統一しました。過去のリリースノートのリンクと日英のガイダンスも更新しています。

## 0.7.0からの更新

Plugin全体を更新し、クライアントを再読み込みしてください。Plugin名`alps`、2つの配布Skillの識別子、ルートの`skills/`配下のパスは変更していません。Plugin全体には引き続き両Skillと参考資料の`examples/`を含めますが、実例はPlugin Skillの検出対象外です。個別のSkillを配布する場合は、そのディレクトリ全体と補助リソースを保持してください。他方のSkillとリポジトリの実例は、必要な依存関係ではなくなりました。

実例のSkillを含む各対象Skillについて、ファイルの許可リスト、同期ルール、直接リンクを`references/locales/ja/SKILL.md`から`references/locales/ja/SKILL.ja.md`へ更新してください。翻訳本文を追加のSkillエントリーポイントとして登録しないでください。実例ツールとの連携では、厳格化した入力、追加した`input_relationship`出力、Pythonの最低バージョンを確認してください。

管理している記述と構成を、変更された成功条件、網羅性のルール、指摘事項で成立を限定できる条件、要求の尊重に関する評価に照らして再評価してください。既存のユーザーの記述やデータを自動変換することはありません。規範、評価、パス契約、機械が解釈する情報の変更を含むため、[バージョン方針](../versioning.md)に基づく1.0未満のMINORリリースです。

再現性のため、移動するブランチではなく、公開された`v0.8.0`タグと、そのタグが指すコミットSHAを記録してください。詳しい変更は[CHANGELOG](../../../../CHANGELOG.md)に記載しています。
