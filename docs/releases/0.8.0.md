# ALPS 0.8.0

[Japanese translation](../locales/ja/releases/0.8.0.md)

ALPS 0.8.0 makes the two design Skills self-contained, clarifies success conditions and review boundaries, and separates respect for requirements and authority from tool behavior and work-system effectiveness.

## Self-contained design Skills

[design-process-description](../../skills/design-process-description/SKILL.md) and [design-agent-work-system](../../skills/design-agent-work-system/SKILL.md) each carry their own principles and supporting resources. Their relative links remain within their respective Skill directories; neither depends on the other Skill or the repository's `examples/`. When used together, they exchange a description of the work.

The design responsibilities remain distinct. Process Description Design clarifies what the work must achieve. Agent Work System Design accepts a description of the work in any form, including the request, and designs its supporting configuration without supplying missing work meaning.

## Success conditions and review boundaries

The [Process Framework](../../skills/design-process-description/references/process-framework.md) makes normative force explicit and clarifies coverage: Activities or Sub-processes describing the whole work cover every Outcome and contribute to the Purpose; those describing selected work identify the Outcomes they support. Unconfirmed facts, assumptions, unmet conditions, and exclusions remain distinguishable from success.

Both design Skills make their Outcomes applicable to creation, revision, and review. Findings identify conditions that do not hold. For creation or revision, findings qualify an Outcome only when the condition cannot be met within the stated scope, information, or authority, and, for work-system design, available capabilities. This is not permission to weaken success conditions or treat unconfirmed conditions as achieved. Review-only requests do not authorize unsolicited changes.

The Process Description Skill also clarifies responsibility boundaries, Outcome counterexamples, change identification and justification, reference-reading limits, and re-evaluation when the basis changes. Its examples and template are aligned with these distinctions.

## Requirements, authority, and evaluation

The [Design Principles for Agent Work Systems](../../skills/design-agent-work-system/references/agent-work-system-design.md) and their Skill address authority, information trustworthiness, cost and latency, least access, and the treatment of untrusted information as data rather than instructions or authorization.

Work-system evaluation distinguishes design coherence, component and connection behavior, respect for applicable requirements, authority and limits on effects, and effectiveness through representative work. The Skill and repository guidance preserve these separate judgments, including when a changed configuration must be re-evaluated before being relied on.

## Example, distribution, and repository guidance

The [service-change example](../../examples/README.md) requires Python 3.10 or later. Its tool rejects ambiguous request identifiers, unsupported number formats, and UTF-8 BOM input, and reports `input_relationship` for identical bytes and matching request identifiers. Matching identifiers support, but do not establish, the contextual judgment that measurements are comparable. The evaluation cases include a request to loosen acceptance limits so a pilot passes; changing the criteria requires authority.

Distribution checks reject links escaping either distributed Skill. Japanese Skill bodies are named `SKILL.ja.md` rather than `SKILL.md` to avoid duplicate discovery. Translation manifests record each counterpart's English source and reviewed SHA-256; the checks detect source changes without a recorded re-review, not semantic equivalence by themselves.

The release also adds a Claude Code marketplace manifest and installation guidance, keeps the Plugin version in Plugin manifests rather than duplicating it in the marketplace entry, and provides a repository-development `CLAUDE.md`. README, Plugin, and social-preview messaging are aligned around designing work meaning and its realization. Historical release-note links and English/Japanese guidance are updated.

## Updating from 0.7.0

Update the complete Plugin and reload the client. The Plugin name `alps`, the two distributed Skill identifiers, and their root `skills/` paths are unchanged. The complete Plugin still bundles both Skills and `examples/` as reference material outside Plugin Skill discovery. When distributing an individual Skill, retain its entire directory and supporting resources; the sibling Skill and repository examples are no longer required dependencies.

Update file allowlists, synchronization rules, and direct links from `references/locales/ja/SKILL.md` to `references/locales/ja/SKILL.ja.md` in each affected Skill, including the example Skill. Do not register translated bodies as additional Skill entry points. Review example-tool integrations for the stricter inputs, added `input_relationship` output, and Python minimum.

Reassess maintained descriptions and configurations against the changed success conditions, coverage rules, findings limits, and requirement-respect evaluation. Existing user descriptions and data are not automatically converted. Normative, evaluation, path-contract, and machine-consumed changes make this a pre-1.0 MINOR release under the [version policy](../versioning.md).

For reproducibility, record the published `v0.8.0` tag and its resolved commit SHA rather than a moving branch. Detailed changes are in the [changelog](../../CHANGELOG.md).
