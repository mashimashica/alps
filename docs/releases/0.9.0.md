# ALPS 0.9.0

[Japanese translation](../locales/ja/releases/0.9.0.md)

ALPS 0.9.0 adds the harness, which applies a process model to concrete work: it runs Processes with agents, records the runs, and records evaluations of their Outcomes. It reads the meaning of the work, the process model and the Skills, and never changes it. The judgment of each Outcome stays separate from the end of a run.

## The harness

The harness instantiates a Process for concrete inputs, output locations, and what each Outcome means in that application. It runs the instance with Claude Code, Codex, a demo agent, or the calling session, and records each run with the inputs it used and which run produced each output. An evaluation records, for each Outcome, a judgment (achieved, not achieved, or unverified), its evidence and limits, and who judged it: a person through the WebUI, or an agent by its MCP client, marked when the same session performed the judged run. An evaluation is shown as resting on stale evidence once one of its inputs or the `SKILL.md` no longer holds what the judged run used, compared by SHA-256.

The WebUI, in English and Japanese, shows the network of Processes and Artifact types, a dashboard, and the instances. The dashboard counts only the three judgments: a run that ended, an output that exists, or an agent's report is never an achieved Outcome. Its findings are of three kinds: problems of the description, such as an Artifact type that no Process produces, for `design-process-description`; problems of the configuration, such as a Skill that is not found or an agent that cannot be started, for `design-agent-work-system`; and what is unverified, such as a run that awaits judgment or an evaluation on stale evidence.

Agents use the harness through its MCP server's twelve tools and five resources. A woken agent, started at the times that `schedules` set or on request, reads the model, the Markdown guidance, and the state, and decides which Processes to run; the harness imposes no order. The `run-process` Skill guides a session that performs a run itself. The harness has no cases, workflow, status machine, or planned dates: an application is identified by its inputs.

A rough request is instantiated by an agent, with no new concept: a wake that is given the request. In the WebUI, **Request**, on every screen, takes what is needed in free text, attachments (files dropped or chosen, which are saved in the workspace's `inbox/`, or Artifacts already there), the Processes that the plan must include, the agent, and whether to run the plan or only instantiate it; the MCP tool `wake` and `alps-harness wake --request` take the same request. The woken agent chooses the Processes that serve the request, instantiates each with criteria that it derives from the request and its assumptions in the notes, runs them unless asked for a plan only, and reports what it planned and why. The wake's record keeps the request, and each instance that its agent makes names it (`createdBy`). The WebUI's form for instantiating by hand is gone; the criteria and notes of an instance are still edited there, and evaluations still recorded. A session can tailor a request itself, as `run-process` now describes.

See the [Harness section of the README](../../README.md#harness) for its use and its safety measures, and [harness/README.md](../../harness/README.md) for its development.

## Plugin integration

Claude Code registers the harness's MCP server from `.mcp.json` and the `/alps:harness` command from `commands/`. The root `package.json` and `bun.lock` hold only the harness's runtime dependencies, which Claude Code installs when it fetches the Plugin; the development tools are in `harness/` and stay out of that install. Codex reads the root `plugin.json` and the Agent Plugins `mcp.json`, which `.codex-plugin/plugin.json` also names. The Cursor adapter is removed: Cursor loads the Skills through the Agent Plugins format, and the harness's MCP server does not start there because Cursor does not expand `${PLUGIN_ROOT}`.

The harness requires Bun 1.3.11 or later on the client's `PATH`. macOS and Linux are supported; Windows is experimental. The design Skills do not need Bun.

## Example and repository

The [service-change workspace](../../examples/service-change/alps-harness.yaml), with its Japanese counterpart, connects eleven fictional Processes through fifteen Artifact types, with three example Skills, synthetic Artifacts, and operations guidance for a woken agent. Its Production Release Skill now states, as its process model does, that a candidate change invalidates the earlier check and approval basis.

The validation workflow runs the harness's type check, lint, format check, and tests on macOS and Linux, and on Windows without requiring them to pass. Repository tests check the MCP server registrations, the command, the runtime-only fetch-time install, the Host adapters, and the harness's version; `mcp.json` is validated against its schema. `localization.yaml` lists the harness's English/Japanese catalogs for locale review.

## Updating from 0.8.0

Update the complete Plugin and reload the client. The Plugin name `alps`, the two design Skills, and their paths are unchanged, and they work without the harness. The Plugin adds the `run-process` Skill, the `harness` MCP server, and the `/alps:harness` command. In Claude Code the tools appear as `mcp__plugin_alps_harness__<tool>`; add permission rules for them as your practice requires, noting that `instantiate`, `run`, `cancel_run`, `finish_run`, `evaluate`, `wake`, and `open_ui` have effects.

Install Bun to use the harness. If Claude Code could not install the harness's dependencies when it fetched the Plugin, or the client does not install them, run `bun install` in the Plugin directory. Tools that read `.cursor-plugin/plugin.json` must read the root `plugin.json` instead.

Workspaces of the earlier standalone harness keep their files: `<case>` in a location pattern is read as `*`, and an unversioned `.alps-harness/state.json` is converted when read, its work items becoming instances without their cases. The timeline, the kanban board, and planned dates are gone. Add `.alps-harness/` to the workspace's ignore rules.

The harness, its MCP server, and the root dependency manifests add machine-consumed formats and repository path contracts, which makes this a pre-1.0 MINOR release under the [version policy](../versioning.md). For reproducibility, record the published `v0.9.0` tag and its resolved commit SHA rather than a moving branch. Detailed changes are in the [changelog](../../CHANGELOG.md).

## Verification with the real agents

On 30 September 2026, on macOS, the harness ran a copy of the service-change example, in a temporary directory, with the real Codex (codex-cli 0.158.0 on a ChatGPT plan, with `model_reasoning_effort="medium"` and a sandbox that writes only the workspace) and the real Claude Code (2.1.96, logged in to claude.ai on a Team plan, with `claude-opus-4-6[1m]`).

- **A Process with Codex.** Requirements Clarification for CHG-002, from `docs/changes/CHG-002/stakeholders.md` to `docs/changes/CHG-002/change-brief.md`, succeeded in 80 seconds and wrote the change brief: one need with four acceptance conditions, and six ambiguities with their consequences for solution choice. It used 96,428 input tokens (81,152 of them cached) and 1,729 output tokens; Codex reports no cost.
- **Its evaluation.** An agent judged the change brief against the two Outcomes: the Claude Code session that did this verification, not the agent that performed the run. It judged both achieved, with limits: the acceptance conditions are the agent's proposals, not approved by stakeholders, and whether the ambiguities are the material ones needs the stakeholders. **A person has not evaluated it yet.** The run's success is not the evidence.
- **A wake with Codex.** In 165 seconds (458,691 input tokens, 404,096 cached, and 4,163 output tokens), the woken Codex read the model and `docs/operations.md`, and called the harness's MCP tools 14 times without asking (`default_tools_approval_mode = "approve"`). As the guidance puts production first, it ran Incident Response for the production observations, then Pilot Measurement for CHG-001, performing both itself; both ended failed, because the example has no production or pilot capability. It judged their Outcomes, mostly unverified, and reported with `finish_run`, status failed, why the work could not be done and what waits. Both runs are listed in the wake run's `started`.
- **A Process with Claude Code.** Requirements Clarification for CHG-002, from the same stakeholder information (the brief that Codex wrote was moved aside), succeeded in 58 seconds for $0.23 and wrote a change brief with one need, three acceptance conditions, and four ambiguities with their consequences for solution choice. The verifying Claude Code session judged both Outcomes achieved, with limits: the acceptance conditions give no bounds, the brief does not speak of conflicts, and ambiguities that are probably material, such as whether the chosen delivery date is a commitment or a preference, are missing. **A person has not evaluated it yet.**
- **Wakes with Claude Code.** The woken Claude Code connected to the harness's MCP server, called its tools without asking, and reported with `finish_run` each time. The first wake (154 seconds, $0.42) judged the Solution Design that a fake agent had made not achieved and started nothing. The second (325 seconds, $0.74), after stakeholder information for a new change CHG-003 was placed, started Requirements Clarification for CHG-003 (56 seconds, $0.16) and Feasibility Assessment for CHG-002 (139 seconds, $0.36), judged four Outcomes achieved, and used 12 requests to the model, exactly the `--max-turns 12` that the verification's configuration set. The two wakes read the guidance's "once its change brief has settled" the opposite way for the same brief: the first took its four open ambiguities to mean that it had not settled, the second took the successful clarification to mean that it had. These judgments are the agents', as the harness leaves them.
- **Found and fixed.** The two runs that the second wake started ran at the same time, and the record of Feasibility Assessment took as its output, and in provenance, the CHG-003 brief that the other run created: the harness compared the whole location pattern of the type, not the instance's own location. Now a run's output at a concrete location is that path alone. Where the agent decides within a pattern, a run alone has every change there; when runs run at the same time, a change that one of them names as its concrete location is not the run's, and the changes in the directories that the run's inputs give the pattern's wildcards are preferred (the input `docs/changes/CHG-003/stakeholders.md` gives CHG-003). A change that runs at the same time still both hold is marked in each record (`sharedWith`), and the assessment reports that its origin is not known; the provenance that the list of Artifacts and the wake's prompt show names one of the runs, the last to end. The woken Claude Code also loaded the account's claude.ai connectors; it is now started with `--strict-mcp-config`, which loads only the harness's MCP server. The harness gave an agent its whole environment, so a server started from inside a Claude Code session passed on the session's marks (`CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_EFFORT`, and the like); for this verification the server was started without them. A Claude Code agent now does not inherit them, and keeps the credentials, the settings, and `PATH`.
- **Reading Claude Code's output.** Glob and Grep calls show their pattern and where they look; a long absolute path keeps its end, where the file's name is; an MCP tool call shows each argument's name with a short value. The MCP servers of the session and whether each connected, the rate limit, and how the session ended by its own account (why it stopped, how long it took, and the tool uses its permissions denied) are events, and denied tool uses are part of a failure. Claude Code's `num_turns` is its tool round trips plus one (23 for the second wake, whose limit was 12 requests); the harness records it as it is, and the WebUI and the `get_run` description say so.
- **Changes from the recorded output.** The fake agents now print the recorded output of Codex (a run and a failure) and of Claude Code (the run of Requirements Clarification above, and a failure when it is not logged in). The harness reads a Claude Code result that says `success` with `is_error` as a failure, taken from its text, and a Codex error that carries the model API's error as JSON as that error's message. A failed MCP call of Codex is marked.
- **Usage.** Claude Code reports tokens, cost, and turns; Codex reports tokens only. The input tokens are now counted alike: all of them, those read from and written to the prompt cache included, as Codex counts (Claude Code's `input_tokens` counts only the uncached part). A run's usage adds `cachedInputTokens`, the input tokens read from the cache, which the dashboard, the run view, and the assessment show.
- **The MCP server's working directory.** Codex starts an MCP server that its configuration names without `cwd` in its own working directory, the project, and the harness finds the workspace; started in the Plugin root, as Agent Plugins requires when `cwd` is omitted, the harness answers `no-model`, whose message now says to pass the project's directory in `ALPS_WORKSPACE` or to start the harness in it. Codex's MCP client declares no `roots`. Claude Code 2.1.96 starts the Plugin's MCP server in the project directory but passes `ALPS_WORKSPACE` as the unexpanded `${CLAUDE_PROJECT_DIR}`; the harness now ignores a value that still holds `${…}` and names no existing path.
- **The Plugin in Claude Code 2.1.96.** `claude plugin validate` reports `$schema` and `displayName` in `.claude-plugin/plugin.json` as unknown keys, which 2.1.96 predates, and exits with a non-zero status; the Plugin loads with them. With `--plugin-dir`, the Plugin replaces the installed one for the session and its MCP server `plugin:alps:harness` found the workspace. Installing a clean clone from a local marketplace (`claude plugin marketplace add` and `claude plugin install`, in a separate configuration directory) copied the Plugin in 5 seconds without installing its dependencies.

The agents' cost: for Claude Code, $1.92 in all by its own account (the run of Requirements Clarification $0.23, the wakes $0.42 and $0.74, and the two runs that the second wake started $0.16 and $0.36); for Codex, 663,509 input tokens (551,552 of them cached) and 6,255 output tokens in all, the two checks of the MCP server's working directory included, on a ChatGPT plan, which reports no cost.

## Not yet verified

The harness's E2E tests drive its command line, HTTP API, MCP server, and WebUI as real processes, with fake agents. They show the behavior of its parts and connections and its safety checks, not that the Outcomes of a Process are achieved. These remain unverified at the time of writing:

- A person's evaluation of the Outcomes of the runs above: every judgment so far is an agent's.
- Requests served by a real agent: they were checked with the fake wake agent only, not with Claude Code or Codex.
- With the real Claude Code: a run that ends with `error_max_turns` or with denied tool uses, and the usage of a run whose result never comes; the fixes above (the outputs of runs at the same time, `--strict-mcp-config`, and the environment an agent inherits), which came after the runs and were checked with the fake agents; and whether a woken Claude Code, with the Plugin installed, also loads the Plugin's own harness server.
- Whether current Claude Code releases run the fetch-time install when they fetch this Plugin from its GitHub marketplace, and within its 60-second limit; whether Claude Code started from a desktop application finds `bun` on its `PATH`.
- In Codex, with the Plugin installed (installing it changes the user's Codex configuration, and it was not tried): whether it starts the MCP server in the project directory or in the Plugin root, where the harness finds no workspace; whether it installs dependencies; and whether `mcp.json` and the `mcpServers` of `.codex-plugin/plugin.json` register the server once.
- A woken Codex's long waits in `get_run`, up to 300 seconds: the harness now gives the MCP server a `tool_timeout_sec` of 330 seconds (Codex's default is 60), which the wake above did not have.
- The checks of MCP server entries by `claude plugin validate`, which the validation workflow runs with Claude Code 2.1.285 (they need 2.1.281 or later), have not been run.
- On Windows: stopping an agent's whole process tree, and the whole test suite.
- When this repository itself is opened in Claude Code, its root `.mcp.json` is also read as the project's MCP configuration, in which `${CLAUDE_PLUGIN_ROOT}` is not set; the effect on repository development and on real agent runs in the example workspace is not examined.
- In whole-suite test runs, the browser that E10 drives has at times stopped answering; its cause is not identified.
