# Experience First

## Purpose

Make user delight the target of the work, ahead of implementation convenience. Foundational thinking governs the *sequence* of work. This principle governs the *target*.

## Outcomes

- Where implementation convenience conflicts with user delight, the choice made is delight, for whoever consumes the work.
- Every feature, control, and option is justified.
- Fewer polished features ship rather than more rough ones, with the details right (transitions, alignment, spacing, feedback, error states).
- Impact is explained from the user's perspective.

## Tasks

The following Tasks are required whenever this principle applies, each with the conditions it states. Numbers identify the Tasks and set no order.

1. When implementation convenience conflicts with user delight, choose delight.
2. Every feature, control, and option must be justified
3. Ship less, ship better (polished experience with three features beats rough one with ten)
4. Prototype before committing (design decisions are cheaper in throwaway HTML than production code)
5. Get the details right (transitions, alignment, spacing, feedback, error states)
6. Tighten the core loop (every feature should serve the central workflow or get out of the way)

## Controls

The user is whoever consumes the work. For a UI that is the end user. For a library or an internal API it is the colleague who imports it. The engineer who maintains the code next is a user too. Weigh their experience the same way, and explain impact from their perspective.

Foundations should serve the experience.

## Constraints

This principle applies when product, UX, or feature-scope tradeoffs come up. When another description cites this principle, that description's own limits on it hold.
