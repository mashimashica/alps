# ALPS形式のpstack

[英語版](../../README.md)

このディレクトリツリーは、pstack Pluginの仕事の記述をALPS形式で書き直したものである。非公式の変換であり、ALPSの二つの設計Skillの参照資料として置く。pstackの作者と提携しておらず、その承認も受けていない。

変換が変えるのは、各仕事の記述の仕方である。仕事そのものは変えない。変換後のファイルに従うエージェントは、上流のファイルに従うエージェントと同じことをする、という想定である。本ガイドは、この主張が裏付けられている箇所、裏付けられていない箇所、変換の過程で分かったことを述べる。

## pstackとALPSの対応

変換は一つの優先順位に従った。上流の仕事の意味を保つこと、次にプロセスフレームワークの要求を満たすこと、次にファイルを短く保つことである。最初の二つを両立できない箇所では、上流の意味を保ち、その不足を記録した。

| pstackでは | ALPS形式では | 理由 |
| --- | --- | --- |
| Skillやプレイブックの題名 | 名称。無変更 | 利用者と他のファイルがすでにその名で呼んでいる |
| 仕事を行う理由。明示されていない | 目的。変換が導出した | フレームワークが要求する |
| 完了とみなす条件。大半は明示されていない | 成果。変換が導出し、上流の文面における根拠をそれぞれ記録した | フレームワークは観察可能な結果条件を要求する |
| 番号付きのステップと、文字の付いたフェーズ | 同じ番号、文字、見出しを持つタスクと活動 | 他のファイルが番号と名前で引用している |
| 番号付けが暗に示す順序 | 制約の下の記述。記載順を既定とし、仕事が必要とする依存関係を個別に述べる | 文書上の順序を実行順序と解釈してはならない |
| 「**Reply:** ...」と報告の形式 | 出力 | 返信は情報項目である。それが存在することは成功ではない |
| 「You own this task. Plan, review, verify.」 | 制約 | 主担当と委任先の間で責任を割り当てている |
| 評価基準、保持リスト、判定用の問い、文体規則 | 統制事項 | 仕事を方向付け、または判断の基準を与える |
| 禁止、承認、エージェントやモデルに対する制限 | 制約 | 許される実行を制限する |
| 24件の原則Skill | その原則を適用する仕事のプロセス記述。適用のきっかけは最初の制約とする | 他の記述が同じファイルを基準として引用する |
| poteto-modeの六つの名前付きの節 | 主な機能に対応する要素の下に、節ごとそのまま置く | 約20のファイルが節の名前で引用している |
| `Task`、`subagent_type`、モデルのslug、ルールのパスなどのHost固有の識別子 | 無変更。上流が置いた文の中に残す | Claude Codeアダプターと上流の生成スクリプトが、文字列の一致でそれらを探す |
| 「Phase A steps 3 and 4 of the **arena** skill」などの引用 | 無変更 | 引用先が名前を保っている |
| frontmatterのdescriptionだけが述べる規則 | 本文にも持ち込む | 本文がプロセス記述である |
| レビューを行うエージェントのペルソナ調の語り | 各規則を平易な言葉で一度だけ述べる。ペルソナと、正確に定められた最初の出力行は、明示した要求として残す | 規則が比喩表現の中にだけ存在してはならない |
| 同梱スクリプト | 無変更。それぞれにツール利用参照文書を添える | 設計原則は、ツールのインターフェースを利用者が得られることを要求する |

変換は、pstackを別のHostへ移植していない。Host固有の識別子を一般的な用語に置き換えていない。不明確だと分かった箇所を修復していない。

## pstackの構成

以下の事実は、Plugin全体と上流リポジトリのスクリプトを読んで得たものである。

- **ルーターは一つ。** `poteto-mode`は、仕事を22のプレイブックの一つに対応付け、そのプレイブックのステップをtodoリストへ写し、ステップの進行に応じて他のSkillへ振り分ける。24の原則Skillの索引を持つ。
- **Skillは入力されたときだけ読み込まれる。** 58のSkillのうち57と、Bennyの3つのSkillすべてが、`disable-model-invocation: true`を持つ。利用者の言葉から読み込まれ得るのは`setup-pstack`だけである。このため、運用者の規則が委任先のエージェントへ届く経路は、`poteto-mode`と`worker.md`だけになる。`worker.md`は、すべての起動メッセージが最初の行で指定する。
- **ファイルは互いを構造で指し示す。** 19のファイルが、poteto-modeの「the Subagents section」を引用する。arenaのフェーズを文字で、プレイブックのステップを番号で、unslopの規則をidで引用するファイルもある。これらの引用を検査する上流のスクリプトはない。
- **モデルの選択は共有情報である。** `setup-pstack`が、9つのロール行を持つ一つのルールファイルを書く。`poteto-mode`、`arena`、`swarm`、`interrogate`と5つのプレイブックが、ラベルによってそれを読む。
- **一つのソースで二つのHost。** CursorはPluginのフォルダをそのまま導入する。Claude Code向けには、上流のスクリプトが二つ目のツリーを生成する。このツリーはファイルを複製し、22のSkillに、アダプター文書を指す1行を挿入する。アダプターは、実行時にCursorの名前をClaude Codeへ対応付ける。スクリプトは、Skillの文面にある正確な語の一致によって、その行が必要なSkillを見つける。
- **同梱ツールは四つ。** 二つはテストスイートを持つTypeScriptのコマンドラインツールである（`watch-pr`、statechartツール）。二つはテストのないシェルスクリプトである（`worktree-audit.sh`、`log.sh`）。

## 変換元について変換が観察したこと

あるファイルに目的と成果を書くには、二つの問いに答えなければならない。この仕事は何のためか。成功したことを人はどうやって見分けるか。上流の文面がそれに答えていない箇所、または二通りに答えている箇所では、変換は文面をそのまま保ち、所見を記録した。

変換の担当は738件の所見を記録した。その後、別の読み手が各所見を上流のファイルと照合し、文面について事実であり、エージェントの行動または成功の判断に実質的に関わり、引用した語で裏付けられるものだけを残した。残ったのは173件である。[変換元の文面に関する所見](../../findings.md)が、証拠とともにそれらを列挙する。

| 所見の種類 | 件数 |
| --- | --- |
| 一つの記述が二通りに読める | 65 |
| 二つの箇所が同じ規則を異なる形で述べている | 44 |
| 状態を変更する行為に、条件が述べられていない | 18 |
| 成功が、成果物または手順として述べられている | 12 |
| ツールが文面と異なる動作をする | 11 |
| 仕事が、同梱されていないものに依存している | 11 |
| 順序が暗示されているだけか、食い違っている | 7 |
| その他（解決しない引用、共有情報、述べられていない目標） | 5 |

例：

- **確認が必要なものの一覧が二つある。** `poteto-mode`は、チームチャットへのメッセージとチケットの更新を、尋ねずに進めてよいとする。それが索引に載せる原則Skill `principle-never-block-on-the-human`は、確認を要する行為に「send external messages」を挙げる。
- **所有者が二つあるログ形式。** Hillclimbプレイブックは9列の`decision.tsv`を規定し、それを`show-me-your-work`経由で記録させる。`show-me-your-work`は、6列、`decisions.tsv`という名前、ちょうど6つの項目を受け取る補助スクリプトを定めている。
- **他のプレイブックと矛盾するきっかけ。** Opening a PRは、自身が「invoked at the end of every other playbook」であると述べる。InvestigationはPRなしで終わり、Multi-phase planは計画を引き渡して止まる。
- **読むファイルによって変わる振り分け。** `poteto-mode`は、無人で進める仕事を`figure-it-out`へ送る。同時に、長い無人の仕事のためのAutonomous runプレイブックも挙げている。
- **定義されない終了状態。** Babysitの`drive`モードは「loops to merge-ready」とする。文面はmerge-readyを定義しておらず、それが指定する監視ツールは、必要な承認がまだない状態でも`READY`を報告する。
- **一つの場合に成り立たない保証。** Worktree cleanupは「Branch refs survive, so no commits are lost」と述べる。それが実行する監査は、detached HEADのworktreeも列挙する。そのコミットを保持するブランチはない。

これらは文面の読みである。作者が意図しているものもあり得るし、エージェントが文脈から解決できるものもあり得る。

### 試行

試行はClaude Codeで実行した。作業するエージェントと審査役は、どちらもClaude Opusである。変換後の側は、上流の生成スクリプトがこのツリーから構築するClaude Code用ツリーを使った。上流の側は、上流がコミットしているClaude Code用ツリーを使った。作業するエージェントには、サブエージェントを起動するツールがなかった。

| 課題 | エージェントが従った文面 | 文面ごとの実行回数 | 従った上流の指示（変換後、上流） | 満たした導出成果（変換後、上流） |
| --- | --- | --- | --- | --- |
| 仕込んだバグをテスト先行で修正する | `tdd` | 2 | 30中30、30中30 | 10中10、10中10 |
| 原因から離れた場所で現れるクラッシュをデバッグする | `principle-fix-root-causes` | 2 | 20中18、20中18 | 8中8、8中8 |
| 課題を実行せずにプロンプトを深める | `sharpen` | 2 | 20中20、20中20 | 8中8、8中8 |
| 専門用語の多いメッセージを言い直す | `bro` | 8 | 48中41、48中42 | 32中25、32中26 |
| 一つのファイルのコメントをレビューする | `agents/comment-sicko.md` | 6 | 132中130、132中128 | 30中28、30中26 |

課題そのものは、どちらの文面でも、すべての実行で成功した。ただし、コメントのレビューでは、それぞれの文面で1回ずつ成功しなかった。

試行が示すことと、その限界：

- **二つの文面を分けたシナリオはない。** 同じ文面での実行どうしの差は、異なる文面での実行どうしの差と同じ程度だった。
- **`bro`。** 最初の4回の実行では、変換後の1回が簡潔でないと採点された。追加の12回の実行では、この差は再現しなかった。76語のメッセージに対し、返信は変換後の文面で平均144語、上流の文面で平均142語だった。この12回の審査役は、どちらの文面でも、すべての返信を、言い直す対象のメッセージより長いと数えた。
- **レビューを行うエージェント。** これは、ペルソナ調の語りを平易な規則として書き直した唯一のファイルであるため、実行回数を最も多くした。12回の実行すべてが、要求された最初の行で始まり、コードを変えず、ライセンスヘッダー、公開APIのコメント、`prettier-ignore`を保持し、`IMPORTANT`のコメントと二つの抑制コメントを削除した。保持の条項をコードから証明できなかった一つのコメントは、変換後の6回中3回、上流の6回中4回で削除された。後半の8回の審査役は、それを保持することは疑いがある場合の規則に反すると判断し、その理由で、それぞれの文面の1回ずつを失敗と数えた。
- **`poteto-mode`。** 三つの指示は、返信からは判定できなかった。原則のファイルが読まれたか、プレイブックのステップがtodoリストへ写されたか、`unslop`が読み込まれたかである。これらは、どちらの文面でも、従わなかったものとして数えている。
- **限界。** 文面ごとに2回から8回の実行、一つのモデル、一つのHost、小さなフィクスチャ、サブエージェントなし。審査役は、どちらの文面が原文かは知っていたが、どの実行がどちらの文面に従ったかは知らなかった。審査役は、作業するエージェントと同じモデルである。これらの試行は、変換した7つのファイルがこれらの課題で原文と同じように振る舞う、という判断を支持する。変換した他の78ファイルについての証拠ではない。

## 運用者が知っておくべき変換の影響

- **poteto-modeの形を写すSkill。** `automate-me`は個人用のモードを下書きし、「The **poteto-mode** skill shows the shape」と述べる。このツリーからそれが下書きするモードは、変換後の形にならう。
- **frontmatter。** Host用フィールドは最上位に残している。Hostがそこで読むためである。厳格なAgent Skillsバリデータは、上流に対するのと同じく、それらを拒否する。
- **名前。** manifestは`pstack`という名前を保つ。アダプターの`pstack:`という接頭辞を有効に保つためである。このツリーを上流のpstackと並べて導入しない。

## 変換が適用しなかった設計上の所見

以下は、表現の変更を超える。提案であり、変換後の文面の一部ではない。

- **Hostへの結び付けを仕事から分離する。** 記述はステップの中でHostのツールを名指ししており、Claude Codeアダプターはその正確な語に依存している。仕事が必要とする各能力を一度だけ述べ、それを一箇所でHostに結び付ければ、一つの記述で両方のHostに対応できる。そのためには、アダプターと上流の生成スクリプトも変更する必要がある。
- **引用された原則をどう適応してよいかを述べる。** 原則Skillは共有の基準として使われている。プレイブックはすでに、所々でそれらを制限または反転している。変換は各原則に、引用する記述自身の制限が有効である、という一文を加えた。許される例外のより完全な記述は、作者に属する。
- **共有情報の所有者を一つにする。** モデルのルールファイルと判断ログは、それぞれ複数のファイルから読まれる。書き手、読み手、変更によって無効になるものを一箇所で名指しすれば、上に挙げた所有者が二つある事例はなくなる。
- **長時間実行するプレイブックの終了状態を定義する。** いくつかのプレイブックは、ツールが報告しない状態で終わる。監視ツールの出力で判定できる成果があれば、その隔たりは閉じる。

## このツリーの使い方

このツリーは参照資料である。試す場合：

- **Cursor。** このツリーは上流のPluginの配置を保っているため、上流のフォルダの代わりに置ける。Cursorでは試していない。
- **Claude Code。** 上流のスクリプトでClaude Code用ツリーを生成する。固定したコミットの上流リポジトリにある`scripts/generate-pstack-harness-trees.mjs`を`scripts/`フォルダに置き、その隣にこのツリーの写しを`pstack/`という名前で置く。両方を含むフォルダから`node scripts/generate-pstack-harness-trees.mjs`を実行する。結果は`harness/pstack/claude-code/`の下にできる。上の試行は、この方法で構築したツリーを使った。
