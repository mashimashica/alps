# 運用の案内

このチームがサービス変更のモデルのプロセスをどう運用するか。人が読み、ハーネスが定時に起こすエージェントも読む。これは案内であってワークフローではない。プロセスに決まった順序はなく、次に何を走らせるかを決める者が、この案内を今のアーティファクトとその評価に照らして判断する。

## 先にすること

- 変更は、設計する前に明確にする。関係者の情報か改善提案が新しく加わったか変わったときは要件の明確化を走らせ、その変更概要が固まったら実現可能性の評価を走らせる。解決案の設計は、固まった変更概要から始める。
- 候補版は、評価する（サービス変更の評価）前に試行で測定し（試行での測定）、本番適用の判断は同じ候補版の試行評価に基づいて行う。
- 本番リリースは、確かめた候補版そのものを承認する変更要求の後に行う。新しい候補版は、それまでの確認と承認を無効にする。測定・評価・判断をやり直す。

## 優先すること

- 本番が最優先である。新しい本番の観測結果が利用者への影響かサービス水準目標の未達を示すときは、ほかの作業を始める前にインシデント対応を走らせる。
- 次に、新しい変更の作業より先に、試行中か本番適用の判断を待っている変更を進める。
- リリースの後に本番の観測結果が増えたら、その変更の振り返りを走らせ、学んだことを改善提案として次の変更に渡す。

## プロセスを走らせないとき

- 候補版を名指しした変更要求がないまま、または本番運用方針が求める承認済みのリリースジョブ以外の方法で、本番リリースを走らせない。
- 前回の実行が判断された後に入力が変わっていないプロセスは、その評価の根拠が古いか、誰かに頼まれたのでない限り、走らせ直さない。
- 実行が正常に終わったことや出力があることを根拠に、成果を達成と判断しない。根拠を読むまでは未確認のままにする。
- サービスの責任者の承認が要る判断は責任者に委ね、責任者を待っているものを報告する。
