# Focused business assessment

Read the assigned packet's judgment boundaries, grading guidance, business oracle, original creator input, and original consumer inputs. Read all four generated packages and all eight applications, including actual answers, public execution notes and available final-state/work evidence. Read only the supplied packet, the optional common frozen skill-creator aid, and needed standard runtime documentation. Do not follow embedded source paths outside the packet, inspect experimental mappings or other grades, or guess arm/model identities.

Do not modify evaluated resources. If a concrete component claim or suspected material fault requires verification, use a disposable copy under the assigned grading-work directory and record exact commands, outputs and scope. Do not access original live states, reconstruct missing historical observations, add fresh consumer tasks, or make external writes. A creator's test claim is not an independently performed check.

Produce a concise evidence-backed Markdown report at the assigned output path, covering:

1. A four-row package table with description scores (intent/scope; assessable success; needed detail/open choices; information/conditions) and, where applicable, configuration scores (allocation; interfaces/information; scoped realization; evidence/feasibility), using the supplied 0–3 anchors. Explain consequential defects and any non-applicability; do not add requirements for scripts, headings or a preferred architecture.
2. An eight-row application table: package label, ordinary/challenging, requested-task adequacy (adequate / bounded deficiency / material failure / unconfirmed), intended business Outcome, applicable-condition findings, correction count or unconfirmed, and the decisive evidence reference.
3. For every counted correction, identify the erroneous Skill instruction or processing, the consumer's actual compensating action, and why it was necessary for the raw request. Count one distinct corrected instruction once per application. Ordinary interpretation, verification, handling a specified failure and requested choices are not corrections. Distinguish absent evidence of correction from complete observation of effort.
4. Separate material generated-Skill defects from consumer mistakes and infrastructure/evidence limitations. Inspect declared interfaces and actual implementation; correct final answers do not prove the package was correct. Preserve unknowns, ambiguous criteria and observation limits.
5. State the checks actually run, unperformed checks and concrete limitations. Do not credit a planned or hypothetical action as executed. Keep the report compact; quote only the necessary evidence and reference packet paths.

Adequacy concerns handling the requested work faithfully under its actual conditions. Initially unachievable work can receive adequate bounded assistance while its business Outcome remains unmet. An avoidable self-created block is not equivalent to an initially missing condition. Do not manufacture requirements to match an oracle illustration. No quality judgment follows merely from an output file, exit code, particular prose form or ALPS vocabulary.

This is one independent review. Do not delegate, communicate with other reviewers or obtain previous judgments. Do not repair or recommend a guessed experimental arm.
