## Material evidence and implications

### 1. Qualification changes the evidence on which approval depends

In `F19/business-input/release_tool.py:24`, `qualify` creates a new sequence; `:26` replaces the qualification record. Promotion requires approval's qualification sequence to equal that current sequence (`:36`). F19's and F27's unconditional qualification tasks therefore invalidate a previously matching approval even when candidate content has not changed. Neither package identifies a necessary reason to replace still-applicable evidence. This adds work and a new approval dependency beyond the brief's prerequisite. F36 explicitly preserves the meaningful choice to use current evidence. F61's wording leaves that choice ambiguous. This finding concerns instructions and the supplied interface, not an observed blocked run. It follows AWS §§2–5 and PF §4's shared-information/change-effect requirements.

### 2. Receiving conflict evidence is not consistently preserved across interfaces

The source requires identifying the affected lines when one `event_id` has differing content (`F03/business-input/brief.md:23`). The written receiving rules mostly preserve that requirement, but static code paths do not:

- F03 keeps only `rows[0]` for each ID and attaches conflict issues only through that retained identity (`F03/package/receiving-review/scripts/review_receipts.py:48`, `:53`). Another affected line, month variant, or order-level identity issue can disappear from per-line judgment evidence.
- F55 likewise retains only the first canonical event, then derives line evidence and conflict flags from retained events (`F55/package/receiving-review/scripts/review_receipts.py:45`, `:47`, `:74`). The global conflict-ID list survives, but does not identify every affected line.
- F42's attempt to recover the earlier line compares its key to pairs such as `("order_id", value)`, not the stored field values (`F42/package/receiving-review/scripts/review.py:40`, `:44`). A conflict spanning different orders need not flag the first line.
- F80 marks entire orders anomalous for event-content conflicts (`F80/package/receiving-review/scripts/review_receipts.py:43`), potentially limiting otherwise sound sibling lines. It also retains conflicting versions as distinct entries and sums them (`:51`, `:60`), without distinguishing that subtotal from quantities of independently evidenced events. A conflict flag warns against final comparison, but does not make the combined subtotal supported.

An agent could revisit the original input; these findings do not establish inevitable misinterpretation. They establish insufficiently faithful processing/evidence supply under AWS §4 and the packages' own stated allocations.

### 3. A local missing condition becomes a global stop

F55 requires all three responsibility values before any processing and rejects the input if any is absent (`F55/package/receiving-review/scripts/review_receipts.py:19`, `:20`); its Skill tells the agent to “stop for correction” on exit 2 (`SKILL.md:26`). A missing warehouse-lead contact can therefore block sound receipt judgments even when no excess requires that role. This conflicts with the brief's “unrelated sound evidence remains usable” (`F55/business-input/brief.md:21`) and the package's own `SKILL.md:33`/`:35` distinction between usable judgments and a blocked draft. Missing global structure can legitimately block work; that does not justify this broader role gate.

### 4. Contradictory coverage is silently replaced

F55 and F80 overwrite matching coverage records (`F55/package/receiving-review/scripts/review_receipts.py:64`; `F80/package/receiving-review/scripts/review_receipts.py:56`). Contrary declarations can therefore end with `complete=true` without exposing their disagreement. The source permits a final comparison only with confirmed complete, valid evidence (`business-input/brief.md:23` in both packages). Last-record selection is neither stated nor justified as a resolution rule. This is an unmet evidence-condition requirement, not a demand for a particular parsing design.

### 5. Interfaces need truthful result and effect descriptions

F42 says nonzero results are explained on stderr (`SKILL.md:27`), but structural validation results are printed on stdout before exit 2; only read/JSON errors use stderr (`scripts/review.py:78`, `:79`, `:80`). F80 calls its helper “read-only” and safe to retry (`SKILL.md:42`), although the documented optional output path is written and can overwrite an existing file (`scripts/review_receipts.py:69`). These mismatches matter under AWS §4's failure/result/state-effect requirements. They do not imply external receiving records were changed.

## Present guidance and limits

Across packages, substantive information roles are generally identifiable without dedicated labels: orders/events and release state are examined Inputs; comparison rules and approval criteria direct judgments; permission, completeness, and sequence govern dependent actions; commands supply capability; returned evidence and assessments are Outputs. Receiving judgment and drafting remain agent responsibilities; releases appropriately reuse the supplied CLI rather than require an unnecessary wrapper. All packages preserve no-live-business boundaries and distinguish intermediate evidence from overall success somewhere in their instructions.

The receiving packages explicitly limit claims from component success; the release packages require production observations and separate uncertainty. This is present evaluation guidance, not evidence that components or whole systems were successfully evaluated. Completed verification and effectiveness remain unconfirmed from the allowed record; absent test reports do not prove tests never occurred. I performed no component runs, business reruns, repairs, or source changes. Physical-format conformance, external references, and actual execution results were not audited. No creator conversations, assignments, hypotheses, consumer observations, or grades were consulted, and no arm-level cause is inferred.
