# ALPS 0.4.0

ALPS 0.4.0 establishes a Process-centered representation model for Agent Skills, adds the packaged ALPS Process Reference Model, and introduces the optional ALPS Markdown Profile v1 Environment Binding. It also aligns the specification and locale path hierarchy, separates distributed Plugin Skills from repository-development Skills, and preserves the distinction between ALPS Conformance and validation of one physical representation.

## Process-centered representation model

A Process is the work that is defined, applied, managed, composed, and assessed. An Agent Skill is the discoverable asset that represents a Process through an authoritative Process Description by default.

Agent Skills can now explicitly represent the other Process Framework constructs through `metadata.alps.kind`:

- `process-model`;
- `process-reference-model`; and
- `process-view`.

Loading one of these non-Process representations activates selection or composition context; it does not invoke a Process. Process Views may describe View-local Activities and Tasks. When they reference source Activities or Tasks, they preserve provenance and Traceability, and View-local descriptions do not silently redefine their source Processes.

## ALPS Reference Model and Skill layout

The ALPS Process Reference Model is now distributed as [`skills/alps-reference-model/SKILL.md`](../../skills/alps-reference-model/SKILL.md). It defines the semantic centers and relationships of the three ALPS reference Processes and can be mechanically compared with their authoritative Process Descriptions.

The distributed Plugin now exposes four Skills:

- `alps-reference-model`;
- `define-alps`;
- `apply-alps`; and
- `manage-alps`.

The root [`skills/`](../../skills/) directory is the source of truth for these distributed Skills. Their `.agents/skills/` entries are repository-development discovery links. The repository-only `review-alps` and `sync-locales` Skills remain ordinary directories under `.agents/skills/` and are not registered as distributed Plugin Skills.

## ALPS Markdown Profile v1

This release introduces the optional Environment Binding `alps-markdown/v1`, documented in [`spec/alps-markdown.md`](https://github.com/mashimashica/alps/blob/v0.4.0/spec/alps-markdown.md).

The profile defines a bounded Markdown and frontmatter representation for Process, Process Model, Process Reference Model, and Process View assets. It includes canonical Skill-reference syntax, typed IR extraction, English/Japanese semantic-shape comparison, deterministic diagnostics and exit statuses, and explicit resource limits.

The binding now follows the ALPS semantic boundary directly:

- a Process requires Name, Purpose, and Outcomes; Activities and Tasks are optional;
- a Process View requires Name, Purpose, Outcomes, and Application in this binding;
- a Process View may contain View-local Activities and Tasks; and
- source declarations and inclusion provenance are required when source Activities or Tasks are referenced, rather than for every View.

The checker is now bundled with the repository-development `review-alps` Process at [`.agents/skills/review-alps/scripts/validate_alps_markdown.py`](https://github.com/mashimashica/alps/blob/v0.4.0/.agents/skills/review-alps/scripts/validate_alps_markdown.py). It is an Application Enabler for repository review and is not part of the distributed `define-alps` Package.

The checker validates only `alps-markdown/v1`. It is not a general YAML, CommonMark, GFM, or ALPS validator, and successful execution does not establish ALPS Conformance, Process execution Conformance, Outcome achievability, or Outcome achievement.

## Resource-role and Host metadata alignment

The `define-alps` Package guidance now distinguishes the concrete roles of:

- the authoritative Agent Skill representation;
- output-creation templates and record resources;
- reference information;
- Environment Bindings;
- Application Enablers;
- Host discovery and presentation metadata; and
- presentation resources.

The English and Japanese Process templates use a plain-scalar discovery description and can be materialized directly into `alps-markdown/v1`-compatible Process representations after their placeholders are replaced. Their physical form remains informative and does not become an ALPS requirement.

Affected OpenAI presentation metadata now refers to ALPS representations and applicable Processes without using the ambiguous expression “ALPS Skill.”

## Specification and locale paths

The public normative assets, locale policy, and Japanese repository documentation now use the following repository paths:

| Previous 0.3.0 path | 0.4.0 path |
| --- | --- |
| `.alps/spec/process-framework.md` | `spec/process-framework.md` |
| `.alps/spec/ALPS-SPEC.md` | `spec/ALPS-SPEC.md` |
| `.alps/spec/locales/ja/process-framework.md` | `spec/locales/ja/process-framework.md` |
| `.alps/spec/locales/ja/ALPS-SPEC.md` | `spec/locales/ja/ALPS-SPEC.md` |
| `.alps/localization.yaml` | `localization.yaml` |
| `docs/ja/` | `docs/locales/ja/` |

The new Markdown Environment Binding is published at `spec/alps-markdown.md`. English remains authoritative and Japanese remains the supported locale. The paired specifications, Process representations, records, repository guidance, templates, and remaining Japanese user-facing text have been aligned while preserving canonical identifiers and normative force.

## Compatibility status

The `define-alps`, `apply-alps`, and `manage-alps` identifiers and their root `skills/` paths are unchanged from 0.3.0. `alps-reference-model` is newly distributed in 0.4.0.

Consumers that pin or synchronize `.alps/spec/`, `.alps/localization.yaml`, or `docs/ja/` must update those references to `spec/`, `localization.yaml`, and `docs/locales/ja/`.

The distributed `skills/define-alps/scripts/check_skill_description.py` preflight from 0.3.0 is not retained. Repository-development profile validation is now available at `.agents/skills/review-alps/scripts/validate_alps_markdown.py` and targets the explicit `alps-markdown/v1` contract.

ALPS remains in initial development. These changes affect normative meaning, representation kinds, repository path contracts, Package boundaries, and an Environment Binding, so this is a MINOR release under the pre-1.0 versioning rules.

The exact release contents are identified by the `v0.4.0` tag and the commit to which that tag points. Pin both the tag and commit SHA when synchronizing ALPS assets.
