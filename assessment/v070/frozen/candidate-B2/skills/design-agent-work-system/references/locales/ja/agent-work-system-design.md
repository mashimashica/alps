# エージェント作業システムの設計原則

[英語版](../../agent-work-system-design.md)

## 1. 適用範囲と用語

本原則は、エージェントを用いて仕事を遂行するシステムの設計を扱う。本書では、**エージェント作業システム**（Agent Work System）を、エージェント、その仕事に必要なツール・情報資源・実行環境、およびそれらの相互作用の組合せと定義する。設計の目標は、適用条件の下で意図した結果を達成できる構成である。

**エージェント**は状況を解釈し、意図した結果に向けて進め方を選択・構成する。**ツール**は、役割と利用条件が定まったインターフェースを通じて処理能力を提供する。**情報資源**は、仕事の解釈・遂行・評価に必要な情報を提供する。**実行環境**は、構成要素が動作するための設備や条件を提供する。一つの構成要素が複数の役割を担う場合も、関係する責務と相互作用を明確に保たなければならない。

**must**（しなければならない）は要求、**must not**（してはならない）は禁止、**should**（することが望ましい）は推奨、**may**（してよい）は許可を表す。要求は明示された範囲内で適用される。必要な設計と評価の範囲は、仕事、その影響、依頼範囲によって決まる。

## 2. 責務と配分

設計では、意図した結果、適用条件、仕事の遂行に必要な能力を識別しなければならない。エージェント・ツール・情報資源・実行環境に責務を配分し、構成の実現と評価に十分な程度に依存関係と相互作用を明確にしなければならない。

判断が必要な箇所では、文脈に応じた解釈・選択・構成をエージェントに残すことが望ましい。確定した計算、変換、検査、選択規則、順序は、適切な実装で信頼できる処理が可能なら、実装に委ねることが望ましい。エージェントは、許可された範囲内で、能力の選択と組合せ、方法の調整、新しい方法やツールの考案・実装を通じて、意図した結果と利用可能な手段の間を埋めることができる。

新しい能力を構築する前に、既存能力の適合性を評価することが望ましい。配分の判断では、構成要素の実際の能力と限界、利用できる情報、誤りの影響を考慮しなければならない。結果を生成する責務とともに、結果を解釈し失敗へ対応する責務も割り当てなければならない。

## 3. 境界と組合せ

構成要素の境界は、関連する責務をまとめ、他の構成要素が知る必要のない内部の決定を隠すように設けることが望ましい。インターフェースは、利用・検証・組合せに必要な情報と操作を公開し、内部変更が利用側へ与える影響を抑えることが望ましい。分割は、凝集度、結合度、変更影響に基づくことが望ましい。

内部モジュールの境界と、エージェントへ公開する操作は、目的が異なる。内部操作の安定した組合せは、意味のある選択を失わずに不要な選択と調整を減らせる場合、一つのツール操作として提供することが望ましい。状況に依存する組合せは、必要な情報と判断を利用できる箇所で選択可能に保つことが望ましい。

構成要素や公開操作の小ささは、責務の明確さと、利用・検証・変更・組合せのしやすさで判断することが望ましい。十分であれば、一つのエージェントと既存ツールで構成してよい。

## 4. 情報とインターフェース

エージェントとツールは、責務に必要な情報を取得できなければならない。設計では、その情報の出所、意味、適用可能性、関係する鮮度を明確にしなければならない。情報の選択や要約では、重要な不確実性と出所を含め、依存する判断に必要な内容を維持しなければならない。

必要な各ツール操作について、正しく利用するために必要な範囲で、次を利用者に明確にしなければならない。

- 責務、適用条件、限界。
- 引数と返される情報の意味を含む呼出し方。
- 実行環境の前提を含む、必要な資源と依存関係。
- 処理の成功、処理の失敗、不完全な結果の区別と、それらが次の行為の判断にどう役立つか。
- 外部状態を変更する場合は、変更対象の状態、起こり得る影響、一部完了後の再試行や継続の条件。

説明と応答は、目的や条件が異なる操作を利用者が区別できるようにすることが望ましい。応答は、その後の判断に十分で関連性のある証拠を提供することが望ましい。情報不足、省略、影響の不確実性は、解釈に影響する箇所で分かるようにしなければならない。

相互作用に問題が生じた場合、エージェントへの指示とともに、ツール、情報供給、環境の改善も検討することが望ましい。

## 5. 実行条件と影響

設計では、その主張が依存する実行条件を、アクセス、依存関係、利用可能な能力、必要な権限や承認を含めて識別しなければならない。必要条件は、それに依存する行為や主張の前に確認しなければならない。不足または未確認の条件は、それに依存する行為と判断を制限しなければならない。独立した作業は、それぞれの適用条件の下で続けてよい。

ツールは、外部サービス、変化する状態、確率的な処理を用いてよい。そのインターフェースは、利用に関係する保証と限界を伝えなければならない。決定性や再現性が必要な場合、設計では、何を再現する必要があるかと、その主張を支える入力、版、状態、環境条件を識別しなければならない。

エラーへの対応では、すでに生じた可能性がある影響を考慮しなければならない。結果が不確かな状態変更操作を再試行する前に、システムは結果として生じた状態を確認するか、意図した再試行を支える回復手段を用いなければならない。ツール処理の成功を示す証拠は、意図した結果と適用条件に照らして解釈しなければならない。

## 6. 評価

評価では、対象、基準、証拠、範囲を識別しなければならない。次を区別しなければならない。

1. 設計の責務、関係、適用条件が整合し、十分であるか。
2. 構成要素とその接続が、関係する条件の下で、定められた動作を満たすか。
3. 意図したエージェント、情報、ツール、環境を用いて、システムが代表的な仕事を有効に遂行するか。

検証は、関係する正常・失敗・不完全な相互作用と、仕事が依存する接続を対象にしなければならない。全体を通じた評価では、仕事から得た証拠を用い、意図した結果と適用条件を評価しなければならない。成果物の存在やツールの正常終了だけでは、有効性は確認できない。

評価では、仮定、未解決の指摘、未実施の検証、検証した事例の限界を識別しなければならない。構成要素のテストや代表的な適用の証拠が支えるのは、検証した範囲内の判断である。指摘の原因に対応する場合は、責務配分、インターフェース、情報、環境の変更に指摘を役立てることが望ましい。

## 7. 適応

モデル・ツール・環境の能力が変わった場合、影響する配分、指示、情報供給、公開操作を見直すことが望ましい。見直しでは、能力の限界を補う誘導と、仕事自体に必要な知識・基準・制約を区別しなければならない。

変更案では、意図した結果と適用条件を維持するか、それらへの変更を明確に定めて正当化しなければならない。変更後の構成を信頼して用いる前に、関係する構成要素の検証と代表的な仕事を通じて、影響する動作を再評価しなければならない。得られた証拠の範囲と限界を明示し続けなければならない。
