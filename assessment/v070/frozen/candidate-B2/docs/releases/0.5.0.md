# ALPS 0.5.0

ALPS 0.5.0 consolidates the Process Framework, ALPS Specification, ALPS Reference Model, and three Reference Process Skills around one authoritative source for each information item. It closes proposition-level semantic residuals in English and Japanese, defines versioned logical Skill identity at the normative ALPS layer, removes the ALPS-specific Markdown language and checker, and replaces that checker with separate standard validation, repository-integrity checks, and cross-layer semantic review.

## Authority and normative structure

The repository now assigns authority by subject:

- the [Process Framework](../../spec/process-framework.md) is the sole normative source for general Process constructs and semantics;
- the [ALPS Specification](../../spec/ALPS-SPEC.md) governs Agent Skill representation, ALPS lifecycle, logical references, integrity, and Conformance specializations;
- the [ALPS Reference Model](../../skills/alps-reference-model/SKILL.md) owns the Names, Purposes, Outcomes, and relationship structure of the three Reference Processes; and
- `define-alps`, `apply-alps`, and `manage-alps` remain the authoritative complete Process Descriptions for those Reference Processes.

Repeated general Process semantics were removed from ALPS or traced back to the Process Framework. Informative examples, records, Host metadata, and templates remain subordinate to those normative sources and do not create additional ALPS requirements.

The former paired Appendix D guidance on Human Oversight, Accountability, and Evidence is removed without relocation.

## Logical Skill identity and Package Binding

ALPS now defines complete logical Skill identity as:

`(package ID, exact version, Skill name)`

Package-qualified references resolve through an explicit Logical Package Scope. Same-scope short references resolve within the `alps` Release Package at one exact version. The applicable Host supplies the physical Package Binding from that logical identity to installed resources.

This repository does not implement a multi-package or multi-version resolver. Physical repository paths and Host discovery metadata remain Environment Bindings rather than normative ALPS identity.

## Semantic and Conformance alignment

The Process Framework and ALPS Specification were reviewed proposition by proposition across subject, modality, action or state, object, condition, quantifier, polarity, exception, scope, authoritative destination, and English/Japanese equivalence.

The resulting alignment includes:

- Task Conformance applies only to in-scope `must` and `must not` requirements stated in Activities or Tasks;
- Tailored Conformance separately covers every in-scope Outcome and every in-scope Activity or Task requirement;
- Description, Process, Reference Process, and Execution Conformance remain distinct claims about distinct subjects;
- when multiple Processes are composed, every provider-Output-to-recipient-Input mapping must be explicit;
- Process Reference Model Names, Purposes, Outcomes, and relationship projections remain aligned with the authoritative Process Skills; and
- Process Instance Record fields preserve the specification boundary for Tailoring, Process Name Traceability, Conformance basis, representation assessment, handoffs, and completion evidence.

The three Reference Process display Names are now the noun phrases ALPS Definition Process, ALPS Application Process, and ALPS Management Process. Their stable Skill identifiers remain unchanged.

## Removal of the ALPS Markdown Profile

The current tree no longer contains the optional `alps-markdown/v1` Environment Binding, its checker, typed intermediate representation, parser, resolver, locale comparator, fixtures, or checker-specific tests. The unratified `alps-markdown/v2` draft is also withdrawn.

No compatibility wrapper, deprecation layer, legacy parser, tombstone specification, or replacement ALPS-specific Markdown language is introduced. ALPS remains independent of one physical Markdown or frontmatter form.

The historical `v0.4.0` tag retains the released v1 specification and checker. Consumers that require that binding must remain pinned to the immutable 0.4.0 tag and commit or migrate to the applicable Agent Skill and Host forms.

## Validation and repository integrity

The new [Validate workflow](../../.github/workflows/validate.yml) keeps three concerns separate:

1. official Agent Skills validation, the fixed root Agent Plugins schema, and official Claude Plugin validation;
2. repository integrity for known files, versions, local Host paths, links, symlinks, locale assets, distribution boundaries, and Process Instance Record behavior; and
3. proposition-level review across the Process Framework, ALPS Specification, Reference Model, Reference Process Skills, record bindings, and English/Japanese counterparts.

Known Cursor, Codex, and OpenAI local paths are checked for relative resolution, root containment, target type, and existence. Cursor and Codex Skill paths must resolve to the sole distributed [`skills/`](../../skills/) root. The independent [`process-instance-record/1` implementation](../../skills/apply-alps/scripts/process_instance_record.py) and its behavioral tests remain in place.

Mechanical validation establishes form and repository integrity only. It does not establish ALPS Conformance, Outcome achievability, Outcome achievement, or Process execution Conformance.

## User-facing guidance and Host presentation

The paired English and Japanese README files now explain ALPS through user Outcomes, a direct installation path, plain-language usage examples, and the separation between Process knowledge, representation kinds, and lifecycle management.

Paired English and Japanese ALPS Reference Model diagrams make the five authoritative handoffs visible. OpenAI-facing Skill names and icons are aligned, and Plugin listing metadata now provides concrete capabilities and starter prompts.

## Compatibility status

The package ID `alps`, all four distributed Skill identifiers, and their root `skills/` paths are unchanged from 0.4.0. Logical Skill identity retains package ID, exact version, and Skill name.

Removal of the released `alps-markdown/v1` binding and checker, together with the normative and Conformance changes above, makes 0.5.0 an intentionally incompatible MINOR release under the pre-1.0 versioning policy. No migration compatibility layer is provided.

ALPS remains in initial development. The exact release contents are identified by the `v0.5.0` tag and the commit to which that tag points. Pin both the tag and commit SHA when synchronizing ALPS assets.
