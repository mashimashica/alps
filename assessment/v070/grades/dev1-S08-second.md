## Defects, consequences, and severity

1. **R17's missing-key policy contradicts the business brief.** D17 line 27 says to refuse key invention; C17 line 31 requires a key. Establishing a stable key for a genuinely new authorization is expressly required, not unauthorized invention. The probe failed safely without booking, but this portion of the supported task cannot be completed by the supplied system.

2. **R17 hides a definitive service conflict; both wrappers fail to match recovered receipts.** C17 obtains the child exit code but does not dispatch on it, discarding the simulator's JSON conflict in favor of a generic unavailable outcome. Subsequent lookup is trusted solely because its state is terminal. C63 preserves the initial conflict, but its reconciliation path also pairs an earlier incompatible receipt with the current caller payload. The public probes produced the exact inconsistent records described above. This is a consequential evidence/identity failure, not a database overwrite: the simulator protected the earlier booking and capacity. D63's explicit matching-receipt instruction gives a careful agent a safeguard, so the component defect must not be described as an inevitable false user answer. D17's blanket interpretation of terminal JSON offers less protection.

3. **R63's recommended reconciliation command is not a complete continuation for `not_seen`.** C63 line 40 returns immediately after printing any successful lookup object. Repeating that command cannot record a decision while the key remains unseen. The observation itself is truthful, but is neither a terminal decision nor an actionable three-outcome wrapper result. No service blockage remained in the probe: direct unchanged-key `reserve` succeeded. This is a preventable incomplete path, not proof that R63 cannot recover at all, and not an actual failure of its challenging application.

4. **Both multi-entry caller files lose updates under permitted concurrent use.** Atomic replacement prevents torn JSON, but does not serialize independent read/modify/write operations. The 12-process tests demonstrated actual losses; no race timing was inferred from source alone. Service receipts and capacity remained correct, while wrapper recovery of lost records failed. Supplied keys and durable user requests can still enable direct lookup/exact retry, so this is not erasure of simulator outcomes. R63's loss of seven automatically established keys is particularly consequential if the caller's output is unavailable after process end, since the caller record is the package's supplied way of making those new keys recoverable. The shared file contained multiple logical requests to the same state, not improperly reused files across separate scenarios. Separate per-request files could avoid this particular race, but that restriction is not supplied as the package's concurrency contract and was not silently imposed as a repair.

5. **Syntax errors are obscured.** The 0-seat probe is outside positive authorized booking inputs, so this is a secondary interface-quality limitation rather than a failed business booking. It nevertheless contradicts R17's advertised invalid-input exit behavior and creates avoidable unresolved records in both wrappers.

No lack-of-`fsync` failure is assigned to R63: file close plus atomic replacement supported the tested process-ended recovery, and sudden power loss is not the requested contract. Neither package is penalized for relying on the original simulator's SQLite transaction for capacity and idempotency. That is the correct reuse boundary and it passed the tested races. The separate caller-state race is the independently evidenced missing protection.

## Comparison and limits

The actual consumer results do not distinguish R17 and R63: both completed both tasks with the expected durable states and truthful answers. R17 provides the more useful unseen-key recovery command; R63 provides the required new-key establishment and initially preserves service conflict information. Both retain important full-contract defects despite the applications' adequacy.

The concurrency probes demonstrate particular naturally scheduled overlapping command batches, not every schedule or crash point. Fault controls established before/after-commit uncertainty only in disposable verification states. No arbitrary loss of files, wrong state-path selection, malicious service response, real-world service, cancellation, or external side effect was tested or required. The full original demonstration key itself was not separately exercised here; the same documented session/party/count and other valid keys were used. Further unknown execution details remain unobserved rather than inferred.
