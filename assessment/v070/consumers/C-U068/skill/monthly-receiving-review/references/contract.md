# Processing contract

Input is a UTF-8 JSON object with `month` (valid YYYY-MM), `orders`, `events`, `coverage` (arrays), and `responsibilities` (object). Missing top-level fields are structural errors. Unknown fields are ignored for calculations, but retained when comparing duplicate records.

- Order: nonempty string `order_id`, `sku`, positive integer `ordered`, and supplied `supplier_contact` string. Missing contact blocks routing, not arithmetic. All original rows appear in the report; identical order rows share a calculation. Differing rows for one order/SKU block its judgment pending source reconciliation.
- Event: nonempty string `event_id`, `order_id`, `sku`, valid `event_month`, signed integer `quantity` (booleans rejected). Exact duplicate JSON objects count once. Different content under one ID is conflicting evidence; no arbitrary winning copy is chosen. Conflicting current-month in-scope variants block their affected lines. Known other months and known outside orders are excluded. Missing month or identity that cannot be localized conservatively blocks all potentially affected supplied lines, explicitly recorded as an issue.
- Coverage: `order_id`, `sku`, `month`, Boolean `complete`. Only matching requested-month declarations count. Missing, false or invalid declarations do not establish completeness. Disagreeing declarations require clarification. Duplicate identical declarations are harmless. Coverage never changes scope.
- Responsibilities: supplied strings `purchasing_coordinator`, `warehouse_lead`, `data_steward`. The supplier contact is on each order row. Empty/missing values become unresolved routing.

Output JSON has `month`, `issues` and `lines` in original order-row order. Each line includes source row index (zero based), coverage, blockers, event IDs, `observed_subtotal`, `net_received`, `status`, `difference` (net minus ordered), and `actions` with responsible role, supplied recipient, next action and unsent draft. `net_received` and `difference` are null unless comparison is supported. Observed subtotal is null when invalid/conflicting events prevent even a reliable subtotal. A zero observed subtotal is calculated from an empty valid event set, never substituted for a missing quantity; it is final only with confirmed completeness. Status `undetermined` requires follow-up, never a final short/excess conclusion.

The script reads inputs without modifying them and creates output exclusively (existing output paths are refused). Without `--output`, JSON goes to stdout. Errors go to stderr with exit 2. Retrying with a fresh output path is safe and has no external effects. Report files contain supplied contact information; keep them within the authorized local work area.
