# プロセスフレームワーク

[英語正本](../../process-framework.md)

> “Or, paraphrasing, pragmatism identifies meaning with formation of a habit,
> or way of acting having the greatest generality possible, or the widest range
> of application to particulars.”
>
> 「言い換えれば、プラグマティズムは、意味を習慣の形成と同一視する。
> ここで習慣とは、可能なかぎり高い一般性、すなわち個々の事例に適用できる
> 最も広い範囲をもつ行為の仕方である。」
>
> — John Dewey, “The Pragmatism of Peirce” (1916), p. 711.

## 1. 目的と規範上の位置付け

本フレームワークは、作業の意図、境界、作業内容、文脈、関係、適用、評価を記述し理解するための、適用領域に依存しない基盤を定める。一度限りの作業を含む、一般的な作業と文脈固有の作業を支え、文脈が許す範囲で実行手段の選択を開いておく。

プロセスの意味は本フレームワークが定める。[ALPS Specification](ALPS-SPEC.md)はこれをAgent Skillへ適用し、その意味論と規範強度を維持しなければならない。両者が矛盾する場合は、本フレームワークを優先しなければならない。

**must（〜しなければならない）**は要求、**must not（〜してはならない）**は禁止を表す。**should（〜することが望ましい）**と**should not（〜しないことが望ましい）**は推奨を表す。**may（〜してよい）**は許可を表す。**typically**は一般的な慣行を、**can**と**could**は可能性または能力を表し、これら最後の表現は規範的効力を持たない。記述では各文の効力と範囲を明確にしなければならない。適用される要求と禁止は、評価方法や主張の有無にかかわらず効力を持つ。

例、注記、慣行、その他の参照情報は参考情報である。それらが説明するプロセス要素の意味や規範強度を変えてはならない。

## 2. 作業、記述、結果

| 用語 | 意味 |
| --- | --- |
| **Process（プロセス）** | 一つ以上の成果を成立させるために、目的の下で行う関連する作業。活動とタスクを記述する場合は、それらによって作業が整合した全体を成すことを説明する。 |
| **Process Description（プロセス記述）** | プロセスの実行そのものとは区別される、その記述。一般的なプロセスも特定の適用も記述できる。 |
| **Process Instance（プロセスの一回の適用）** | 特定の文脈におけるプロセスの一回の適用。実際の結果は記述とは別に評価する。 |

すべてのプロセス記述は、**Name（名称）**、**Purpose（目的）**、**一つ以上のOutcomes（成果）**を含まなければならない。これらは意味の中核であり、適用と評価の共通の参照点となる。

| 要素 | 意味 |
| --- | --- |
| **名称** | 作業とその中心的な関心を識別し、関連する範囲で他の作業と区別する。 |
| **目的** | 作業を行うための関連する高水準の目標を述べ、意図する成果を包含する。 |
| **成果** | 作業によって成立する、観察可能で評価可能な結果条件。 |

名称は簡潔であることが望ましい。目的は、隣接する作業と重なる場合には境界を明確にすることが望ましい。独立した目標を結合したり、活動を単に要約したりしないことが望ましい。関係者への便益は目的を達成する価値を説明するものとして示してよいが、成功の判断に用いる成果とは区別する。

各成果は、一つの観察可能な結果条件を述べなければならない。独立した結果を一つの成果に結合してはならず、達成を判断するときに区別できなければならない。各成果は、記述の適用範囲全体で意味を保ち、目的に関連し、他の成果と合わせて目的を満たすために十分でなければならない。レビューではこれらを確認しなければならない。各文は一つの意味を担い、単独で参照されても意味が通るだけの文脈を含むことが望ましい。簡潔さのために独立した目標、結果、行為を曖昧にしてはならない。

タスクは行為を述べ、成果は結果条件を述べる。**Output（出力）**は、作業によって生成または更新される製品、情報項目、サービスである。出力を作成したことだけを成果として述べてはならない。出力は成果の証拠になり得るが、その存在だけでは成功は成立しない。例えば、説明は出力であり、受け手が実際に示した理解は成果である。

## 3. 作業内容と必要な詳細

活動、タスク、入力、出力、統制事項、制約、実行支援要素、開始基準、完了基準は、記述の目的と、作業の理解・適用・評価に必要な詳細に応じて含める。記載は任意であるが、使用する場合の意味と関係は本フレームワークに従う。記述は必要な詳細を含まなければならず、空の任意セクションや網羅性だけを目的とする項目を含めてはならない。適用範囲が曖昧になる場合は、関係する箇所で明確にする。適用する文脈や正本の識別情報は、記述内または関連情報で表せる。

**Activity（活動）**は、プロセス内の凝集性を持つタスクの集合である。関連する行為を、プロセス全体より狭い継続的または反復的な機能としてまとめ、その寄与を理解できるようにする。活動内のタスク同士は、活動外のタスクよりも密接に関係することが望ましい。

**Task（タスク）**は、一つ以上の成果を支える個別の行為を述べる。その操作、対象、規範上の効力を明確にしなければならない。活動内に記述するタスクは、その境界内で可能な行為をすべて列挙する必要はない。

プロセスの作業を記述する活動とサブプロセスは、全体としてすべてのプロセス成果を包含し、プロセス目的を満たさなければならない。成果との関係は、一対一、一対多、多対一、多対多のいずれでもよい。レビューでは、この網羅範囲と、記述されたタスクの寄与を確認しなければならない。活動は、分けて扱うことが有用な場合、固有の名称、目的、成果を持つ**Sub-process（サブプロセス）**として記述できる。

プロセス、サブプロセス、活動には普遍的な大きさの境界はない。成果と主要な出力は通常、プロセス境界の識別に役立つ。中間出力だけを理由に別のプロセスが必要になるわけではない。境界、責任、関係を明確にする場合に作業を分け、理解や利用を損なう階層は省く。実行者やツールの違いだけでプロセス境界は決まらない。他のプロセスへの依存は、必要な関係を明確に保ちながら、実行可能な範囲で減らすことが望ましい。

一般的な記述では、実行者、ツール、方法、測定指標、管理方法、順序の不必要な固定を避けなければならない。記述するのは実行に必要な機能的関係である。特定の文脈で必要な方法や順序は、その範囲と効力を示して記述してよい。**Procedure（手順）**は順序付きの段取りを規定する。活動とタスクは作業を記述するものであり、その文書上の並び順を実行順序と解釈してはならない。必要な時間的依存関係は、制約として明示しなければならない。

## 4. 境界要素と情報

要素の各出現は、ファイル名、媒体、場所によらず、作業において果たす機能で分類する。

| 要素 | 機能 |
| --- | --- |
| **Input（入力）** | 結果を得るための素材として作業が作用する項目。作業で調べる情報や変換する情報を含む。 |
| **Output（出力）** | 作業によって生成または更新される製品、情報項目、サービス。 |
| **Control（統制事項）** | 実行を方向付け、または作業や結果を判断する基準を与える。 |
| **Constraint（制約）** | 許される実行または適用条件を制限する。 |
| **Enabler（実行支援要素）** | 実行を可能にし、または支える能力や資源を与える。 |

基準として用いる方針は統制事項であり、改訂対象の方針は入力である。作業を実行する人、Agent、ツール、実行環境は実行支援要素である。その利用の制限は制約である。同じ資源が異なる役割を持つことがあり、各役割を識別できなければならない。

**情報項目**は、記憶媒体や表現形式によらず、一つの単位として扱う識別可能な情報のまとまりである。出力を名付けても、文書や固定成果物の作成が必要になるとは限らない。出力には最終結果、中間作業成果物、他の作業と共有する情報を含められる。

代表的な変換は入力、活動、出力を関係付ける。活動が入力に作用し、実行支援要素が作業を支え、統制事項が方向付け、制約が制限する。代表的な入力と出力は、実行の一つの可能な方法を例示する。それを唯一許された手段、または記述全体の要求の代わりとして読んではならない。

**開始基準**は、対象作業を開始できる条件を述べる。**完了基準**は、完了できる条件を述べる。これらはスケジュール上の位置ではなく条件を定める。承認を含む必須条件は、それが適用される行為の前に確認しなければならず、未確認の条件は、それに依存する行為を妨げる。他の作業は、それぞれに適用される条件の下で進められる。出力の完成を成果の評価の代わりとしてはならない。

統制事項、制約、実行支援要素は、個々の要素に関連付けても、複数の記述で共有してもよい。共有要素は、その範囲、例外があればその内容、文脈限定の変更の可否を、直接記述するか参照によって識別しなければならない。集合への所属や文書への参照だけで、すべての要素がすべてのプロセスへ適用されることにはならない。宣言した範囲に共通の要素は、一度記述し、適用箇所から参照してよい。

**Traceability（トレーサビリティ）**は、成果、活動、タスク、情報項目の関係を識別可能にし、それらの整合性と変更の影響を検討できるようにする。意図する利用に十分な詳細で、作業と必要な入力・出力を、それらが支える成果へ関係付けることが望ましい。

プロセス間では情報を交換するほか、同じ情報を繰り返し参照・更新できる。必要な関係については、情報の意味、範囲、利用条件、関連する変更影響を明確にしなければならない。どの作業が参照・変更し、変更後にどの判断や結果の再検討が必要かを識別する。受け渡しは提供側の出力を受取側の入力へ関係付ける。共有情報は、複数プロセス間の反復的な相互作用も支えられる。保存と調整の仕組みは利用環境の責務である。

## 5. プロセスを組み合わせた適用

プロセス、活動、タスクは、目的と適用条件に応じて選択し、組み合わせられる。次の関係は、適用の異なる側面を表す。

| 関係 | 意味 |
| --- | --- |
| **Concurrency（並行）** | 同じ構造水準で、少なくとも二つのプロセスを並行して適用する。 |
| **Iteration（反復）** | 同じ構造水準でプロセスまたはプロセス集合を再適用する。プロセス間の反復的な相互作用を含む。 |
| **Recursion（再帰）** | 適用対象の連続する構造水準でプロセスまたはプロセス集合を再適用する。 |
| **Integration（統合）** | 一つの水準内で完全性を、水準間で整合性を成立させる。 |
| **Incremental application（増分的適用）** | 意図する結果または範囲の、利用可能な部分を順次成立させる。 |

これらの関係は独立しており、組み合わせられる。増分的適用は、どの部分を成立させるかに関係し、反復は再適用に関係する。構造水準は適用対象に属し、それだけで組織や実行者の階層を意味しない。

反復では、判断と理解の進展に伴い出力を具体化できる。再帰では、ある水準の出力が別の水準の入力となり得る。出力が変更された場合は、影響する入力と判断を再検討しなければならない。実際の流れは、適用の目的と条件に従う。関係の名称だけで順序は規定されない。対象や文脈の変化がプロセスの選択や実施時期に影響する場合は、それらを見直さなければならない。

## 6. モデル、ビュー、参照

| 構成概念 | 役割 |
| --- | --- |
| **Process Model（プロセスモデル）** | 相互に関係するプロセスと、それらの構成や適用を理解するための関係を整理する。 |
| **Process Reference Model（プロセス参照モデル）** | 識別されたプロセス記述、その目的と成果、プロセス間の関係によって、比較や評価の共通基盤を提供する。 |
| **Process View（プロセスビュー）** | 特定の関心に沿い、複数のプロセス記述から要素を選択して説明する。 |

これらは通常の参照資料として表せる。出典のプロセス記述を参照しなければならず、管理のために目的や成果の定義を重複保持してはならない。領域別のフレームワークでは、プロセス集合と共通の用語を用いて選択と構成を支えられる。**ライフサイクルモデル**は、対象の生涯との関係でプロセスと活動を整理する。その関係と順序は適用に応じて定まる。

ビューは、出典の識別情報と必要なトレーサビリティを維持しなければならない。出典の要素を選択し、説明し、または変更を提案できる。その場合、提案と局所的な追加を出典の要求と明確に区別する。見せ方の変更だけで義務や成功条件を変えてはならない。作業を整理する参照資料はプロセス記述とは区別され、独立して定義する作業には固有の名称、目的、成果が必要となる。

正本の記述は、通常のリンクまたは識別情報によって一意に識別できなければならない。再現性が必要な場合は、適用される版、commit、digest、または同等の情報を参照に添える。必要な参照は、それぞれ意図した対象を識別しなければならない。対象を確認できない場合は、不足する参照と影響範囲を未確認として報告し、同名資料や別版に置き換えない。

要約、翻訳、例、ビューは、正本の意味と規範強度を維持しなければならない。出典の内容と解釈や局所的な追加を区別するために必要な箇所では、出典を識別できなければならない。翻訳は第二の正本ではない。

## 7. 文脈、具体化、変更

**Process Instantiation（プロセスの具体化）**は、一回の適用を、その文脈に十分な詳細で記述する。適用される要求から、その適用に固有の成功基準を導き、それを達成するための作業、資源、条件、実施時期を識別する。これらの詳細は、適用するプロセスと整合しなければならない。

**Tailoring（テーラリング）**は、プロセス記述またはライフサイクルモデルを、宣言した文脈のニーズと条件に適応させる。許された範囲内で、適用する名称、成果、活動、タスク、境界要素を変更できる。名称、目的、成果の整合性を保ち、出典との関係を識別できる状態に維持しなければならない。文脈は一回の適用にも、複数の適用のまとまりにも及び得る。

具体化は一回の適用を具体的にし、テーラリングは適用内容を変更する。テーラリングしたプロセスを具体化することもできる。記述が既に許容する文脈固有の選択は、それ自体では記述の変更に当たらない。

正本の記述の変更、適用内容の文脈限定の変更、見せ方の変更を区別する。変更では、対象となる出典と要素、範囲、根拠、影響、必要な再検証を識別しなければならない。影響する要求と関係者のニーズ、リスク、利用可能な能力と資源、適用される統制事項と制約を考慮する。詳細と厳密さの程度は、これらの条件に見合うことが望ましい。

権限と承認は、利用環境の条件に従う。文脈限定の変更によって、正本を暗黙に再定義したり、外部から課された要求を除いたり、禁止を免除する権限があると示唆したりしてはならない。条件が変わった場合は、仮定と適応の判断を見直すことが望ましい。再検証では、関係する成果、作業、条件、参照、共有情報、翻訳への影響を扱わなければならない。その結果と未解決の限界を明示しなければならない。正本、適用する記述、変更、判断根拠の保存と版管理の方法は、利用環境が定める。

## 8. 評価と改善

評価では、対象、範囲、適用基準、証拠、そこから得た判断を識別しなければならない。証拠は判断を支えるものであり、判断そのものではない。次の問いを区別する。

| 対象 | 問い |
| --- | --- |
| 記述の妥当性 | 目的、成功条件、境界、参照、作業、必要な詳細は、整合し利用可能か。 |
| 実行結果 | 今回の適用で実際に何が起き、どの成果が達成されたか。 |
| 要求の充足 | 適用される必須条件と禁止が守られたか。 |

**レビュー**は、記述、作業、結果を適用基準に照らして評価する。**監査**は、適用される要求の充足を示す証拠を検討する。範囲、基準、証拠によって、どの問いに答えるかを明確にしなければならない。**Decision Gate（判断ゲート）**は、明示した基準の下で先へ進むかを判断する仕組みであり、プロセス記述の段階や構成要素ではない。ゲートの通過で成立するのは、その基準と証拠が裏付ける事項だけである。

記述レビューの成功を実行成功として報告してはならない。出力、承認、形式検証の成功だけから、実行成功を推定してはならない。代表的な例や試行は適用可能性の判断を支え得るが、あらゆる文脈での証明として報告してはならない。

**Capability（能力）**は、意図する結果を達成する能力に関係する。**Maturity（成熟度）**は、プロセスまたはその実装がどの程度確立され、管理され、一貫した実行が可能であるかに関係する。これらの特性には、評価する文脈に関連した証拠が必要であり、一回の適用の成功や要求の充足だけでは成立しない。能力だけで要求の充足が成立することもない。有効性は目的と成果を通じて評価でき、便益と費用は改善の判断に役立つ。

評価に用いる測定では、必要な情報を、定義した測定項目、収集データ、分析、指標、それらが支える判断へつなげることが望ましい。指摘と教訓は変更に役立てられ、その効果を意図した結果に照らして評価できる。実行、承認、測定、記録の仕組みは利用環境が提供する。

未確認の事実、仮定、未達成の条件、適用除外は区別可能に保たなければならない。適用除外には適用可能性に関する根拠が必要であり、証拠の不足を要求の適用外判定の理由としてはならない。これらを暗黙に成功へ変換してはならない。指摘では証拠の不足とその影響を明らかにしなければならない。
