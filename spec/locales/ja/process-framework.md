## 1. 目的と規範上の位置付け

本フレームワークは、作業の目的、成功条件、必要な境界を、実行手段から独立して理解・適用・評価できるように、プロセス記述の意味を定める。一般的な作業と文脈固有の作業を対象とし、一度限りの作業も含む。再利用は効果であり、対象とするための条件ではない。

プロセスの意味は本フレームワークが定め、[ALPS Specification](ALPS-SPEC.md)がAgent Skillへの対応付けを定める。両者が矛盾する場合は、本フレームワークを優先しなければならない。実行、保存、権限、承認、版管理は利用環境の責務である。本フレームワークは実行エンジン、管理手続き、認証制度、記録形式を規定しない。

**must（〜しなければならない）**は要求、**must not（〜してはならない）**は禁止を表す。**should（〜することが望ましい）**と**should not（〜しないことが望ましい）**は推奨を、**may（〜してよい）**は許可を表す。**can（〜できる）**は可能性を表し、例や一般的な進め方は参考情報である。記述では各文の効力を明確にしなければならない。要求と禁止は、評価方法や主張の有無にかかわらず、その適用範囲内で効力を持つ。成果を評価するという選択によって、必須の行為や禁止が解除されることはない。

## 2. 作業、記述、一回の適用

| 用語 | 意味 |
| --- | --- |
| **Process（プロセス）** | 目的と一つ以上の成果に向けられた、関連する作業。 |
| **Process Description（プロセス記述）** | 作業そのものの実行とは区別される、作業の記述。一般的なプロセスも特定の文脈の作業も記述できる。 |
| **一回の適用（Process Instance）** | 特定の状況における記述された作業の実際の実行。その結果は記述とは別に評価する。 |

すべてのプロセス記述は、**Name（名称）**、**Purpose（目的）**、**一つ以上のOutcomes（成果）**を含まなければならない。

| 要素 | 機能 |
| --- | --- |
| **名称** | 関連する範囲で作業を区別する簡潔な名称によって、作業を識別する。 |
| **目的** | 作業を行う理由と、成功条件が寄与する目標を述べる。 |
| **成果** | 成功を評価できる、観察可能な結果状態を述べる。 |

各成果は、行為や単なる成果物の作成ではなく、結果状態を記述しなければならない。成果は目的に関連し、全体として目的を満たすために十分でなければならない。レビューでは、関連性と全体としての十分性の両方を確認しなければならない。成功の判定方法を記述したことは、成功が実際に生じた証拠ではない。

**Output（出力）**は、作業によって生成または更新される製品、情報項目、サービスである。出力は成果の証拠になり得るが、その存在だけを成功とみなしてはならない。作業には固定された成果物の生成を必要としないものもある。例えば、説明は出力であり、受け手が実際に示した理解は成果である。

## 3. 必要な詳細と実行手段

活動、タスク、入力、出力、統制事項、制約、実行支援要素、開始基準、完了基準は任意である。作業の理解・適用・評価に必要な場合だけ含めなければならない。空の任意セクションや網羅性のための「適用外」欄を設けてはならない。Context、ID、versionは一律の必須項目ではない。必要な適用範囲が不明確な場合は、関係する箇所で明確にしなければならない。独立した文脈セクションは必須ではない。

**Activity（活動）**は関連する行為をまとめる。**Task（タスク）**は成果に寄与する行為を、操作と対象が識別できるように記述する。タスクの効力を明確にしなければならない。作業詳細を含める場合は、レビューで成果への寄与を確認し、対応する作業がない結果状態を明らかにしなければならない。固定の分解構造や対応表は必要ない。

一般的な記述では、実行者、ツール、方法、順序の不必要な固定を避けなければならない。特定の文脈で本当に必要な方法や順序は、その範囲を明確にした適用条件として記述してよい。文書の並び順を実行順序と解釈してはならない。必要な依存関係は明示しなければならない。それ以外の作業は、必要に応じて反復、並行、複数の階層で実施してよい。必須の実行パターンはない。

作業を分けるのは、分けることで目的、成功、境界が明確になる場合だけとする。ツールや実行者の違いだけでは、別のプロセスにする必要はない。すべての記述をライフサイクルモデルへ当てはめることなく、隣接作業との必要な境界を理解できなければならない。

## 4. 条件と情報の関係

要素は、ファイル名、媒体、ディレクトリではなく、記述対象の作業における機能で分類する。

| 要素 | 機能 |
| --- | --- |
| **Input（入力）** | 作業で調べ、素材として用い、または変換する情報やその他の項目。 |
| **Output（出力）** | 作業によって生成または更新する製品、情報項目、サービス。 |
| **Control（統制事項）** | 作業を方向付け、または評価基準を与えるもの。 |
| **Constraint（制約）** | 許される行為や適用条件を制限するもの。 |
| **Enabler（実行支援要素）** | 作業を可能にする能力や資源を供給するもの。 |

基準として用いる方針は統制事項であり、改訂対象の方針は入力である。作業を実行する人、Agent、ツール、環境は実行支援要素である。それらの利用制限は制約である。同じ資源が異なる役割を持つことはあるが、役割を混同してはならない。

**開始基準**は対象作業を始める条件を、**完了基準**は完了を宣言する条件を示す。必須条件と承認は、それが適用される行為の前に確認しなければならない。不足または未確認であれば、対象の行為を進めてはならない。独立して実施できる分析や草案作成は、許可された範囲で続けてよい。出力の完成を成果の評価の代わりにしてはならない。

プロセス間では情報を交換するほか、同じ情報を繰り返し参照・更新できる。理解・適用・評価に必要な関係について、情報の意味、範囲、利用条件、関連する変更影響を記述で明確にしなければならない。どの作業が参照・変更し、変更後にどの判断や結果を再検討する必要があるかを識別する。共有情報を直列の受け渡しだけで表すと作業を誤って表現する場合、そのように単純化してはならない。保存、調整、変更の仕組みは利用環境が提供する。

## 5. 正本、参照、ビュー

正本の記述は、通常のリンクまたは識別情報によって一意に識別できなければならない。再現性が必要な場合は、適用される環境の版、commit、digest、または同等の情報を参照に添える。必要な参照は、それぞれ意図した対象を識別しなければならない。対象を確認できない場合は、不足する参照と影響範囲を未確認として報告する。同名資料や別版に置き換えてはならない。

要約、翻訳、例、ビューは、正本の意味や規範強度を暗黙に変更してはならない。出典の内容と解釈や局所的な追加を区別するために必要な場合は、出典を識別しなければならない。翻訳は第二の正本ではない。

**Process Model（プロセスモデル）**、**Reference Model（参照モデル）**、**View（ビュー）**は、複数の記述の関係や横断的な関心を整理する通常の参照資料として設けてよい。出典のプロセス記述を参照しなければならず、管理用に目的や成果の定義を重複保持してはならない。ビューは出典要素を変更せずに選択・説明できる。局所的な提案は出典の要求と区別しなければならない。見せ方だけの変更によって、作業の義務や成功条件を変更してはならない。

プロセスではない参照資料を、Agentが読み込むことやSkillと並んで表示されることだけを理由に、プロセスとして扱ってはならない。独立して定義される作業が必要なら、その作業の目的と成果を記述する。特別な型メタデータや呼び出し体系は不要である。

## 6. 変更

正本の変更、適用内容の文脈限定の変更、見せ方の変更を区別する。変更では、元の意味と変更後の意味を混同しないために十分な詳細で、対象となる出典と要素、範囲、根拠、影響、必要な再検証を明確にしなければならない。意味を変えない文脈上の解釈は、それだけでは出典の変更に当たらない。

権限と承認は利用環境の適用条件に従う。特定の管理Skillは必要ない。文脈限定の変更によって、正本を暗黙に再定義し、外部から課された要求を削除し、または禁止を解除する権限があると示唆してはならない。再検証では、関係する成果、条件、参照、共有情報、翻訳への影響を扱わなければならない。結果と未解決の限界を明示しなければならない。これらの事実の保存方法は利用環境が定め、固定の変更記録は必要ない。

## 7. 評価と不確実性

評価では、対象、範囲、適用基準、検討した証拠、そこから得た判断を明確にしなければならない。証拠は判断を支えるものであり、判断そのものではない。次の問いを区別する。

| 対象 | 問い |
| --- | --- |
| 記述の妥当性 | 目的、成功条件、境界、参照、必要な詳細は整合し、利用可能か。 |
| 実行結果 | 今回の適用で何が起き、どの成果が達成されたか。 |
| 要求の充足 | 適用される必須条件と禁止は守られたか。 |

記述レビューの成功を実行の成功として報告してはならない。成果物の生成、承認、形式検証の成功だけから、実行成功を推定してはならない。代表例や試行は適用可能性の判断を支えられるが、あらゆる文脈で成立する証明として報告してはならない。

未確認の事実、仮定、未達成の条件、適用外を区別できる状態を維持しなければならない。適用外には適用可能性に基づく根拠が必要であり、証拠不足は要求を適用外とする理由にならない。いずれも暗黙に成功へ変換してはならない。指摘では証拠不足とその影響を明らかにしなければならない。ALPSは評価状態enum、診断スキーマ、認証の主張を定義しない。
