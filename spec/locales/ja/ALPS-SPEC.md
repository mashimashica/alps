# ALPS Specification

[英語版](../../ALPS-SPEC.md)

## 1. 適用範囲と規範上の位置付け

本仕様は、プロセス記述とエージェント作業システムの設計をAgent Skillにおいて統合する。[プロセスフレームワーク](process-framework.md)は、プロセスの意味、関係、適用、評価を定める。[エージェント作業システムの設計原則](agent-work-system-design.md)は、エージェント・ツール・情報資源・実行環境の構成と相互作用を定める。それぞれの対象について各参照元が優先する。本仕様は、それらの対応関係とSkillへの適用を定める。

物理的な`SKILL.md`の形式は[Agent Skills形式](https://agentskills.io/specification)が定める。以下の対応付けは、プロセスを記述するSkillに適用する。

## 2. 対応付け

| Agent Skillの内容 | プロセスとしての意味 |
| --- | --- |
| frontmatterの`name` | 発見に用いるSkill識別子。 |
| frontmatterの`description` | 作業とSkillの適用場面の要約。 |
| 本文タイトル | プロセス名称。 |
| 本文の目的と成果 | 作業の目標と、観察可能な結果条件。 |
| 必要に応じた他の本文内容とリンク先資源 | フレームワークが意味を定める、作業詳細、境界要素、適用条件、参照情報。 |

本文には、名称を示すタイトルと、目的と成果をそれぞれ独立したセクションとして含めなければならない。見出しにはPurposeとOutcomes、または文書の言語でそれらに対応する語を用いる。成果のセクションには一つ以上の箇条書きの項目を含め、各項目に一つの成果を記述しなければならない。追加の要素は、必要な詳細に応じて含める。

作業詳細は「活動とタスク」のセクションを用い、活動を小見出し、その下のタスクを番号付きリストで表すことが望ましい。まとまりを設けても有用な区別が生じない場合は、「タスク」のセクションを用いてよい。各タスクの行為と規範強度は、その文、またはリストに適用される明示的な記述によって明確にしなければならない。番号はリストの項目を識別するものであり、必要な実行順序は制約として記述しなければならない。他のプロセス要素を独立して扱うことが有用な場合は、その要素名または翻訳した対応語をセクション見出しに用いることが望ましい。

NOTEは、`NOTE`で始まるMarkdownの引用ブロックとし、説明対象の文章の直後に、その配置から適用範囲が明確になるように置かなければならない。リスト項目に付くNOTEは、その項目内に字下げしなければならない。同じセクション内の複数の注記を区別するために、`NOTE`の後へ番号を付けてよい。番号付き注記を参照する場合は、そのセクションを識別しなければならない。

NOTEは参考情報である。範囲、用語、根拠、具体例、関係を説明してよい。要求、禁止、推奨、許可は、NOTEの外に記述しなければならない。NOTEは、説明する内容の意味と規範強度を維持しなければならない。理解や適用を助ける説明がある場合に、NOTEを含めてよい。

frontmatterとHost表示は、記述の意味と範囲に整合しなければならない。発見情報は記述を要約するものであり、その代わりにはならない。Skillの読込みは、その作業が実行されたことを示さない。参照資料は、プロセス記述と区別可能でなければならない。

## 3. 仕事の記述と実現を支えるシステム

プロセス記述の設計は、仕事の意味、関係、適用条件が整合し、理解・適用・評価に十分であるかを評価する。エージェント作業システムの設計は、仕事を実現する構成と、その実現可能性・有効性の証拠を評価する。必要な作業詳細、方法、順序は、フレームワークが定めるとおり、プロセス記述に含まれる。

実現を支える構成を記述する場合、仕事に用いるエージェント・ツール・実行環境は、実行支援要素としてその記述へ対応付けなければならない。資源は、個々の仕事で果たす役割に基づいて分類しなければならない。処理に利用するスクリプトは実行支援要素であり、作成する対象であれば出力である。調べたり変換したりする情報は入力、仕事の方向付けや評価に用いる情報は統制事項となり得る。関係するつながりごとに、その役割を識別しなければならない。

ツールは、能力の供給とともに、統制事項を実装し、制約を強制する機構にもなり得る。その場合は、適用する規則や制限、その参照元と範囲、操作がそれらをどう適用するかを、対応関係として識別しなければならない。規則や制限は、文書、設定、コードに記述してよく、その意味には識別可能な共通の参照元を用いる。選択したツールや環境による限界は、仕事の要求と区別しなければならない。実行の可能性や成果の評価に関係する場合は、その影響を明確にしなければならない。

タスクがツールに依存する場合、ツール操作が仕事へどう寄与し、その結果が成果の評価をどう支えるかを、対応関係として説明しなければならない。タスクの境界とツールのインターフェースは、それぞれの責務に応じて設計しなければならない。仕事の遂行や評価に必要な場合、プロセスの入力・出力の意味を、ツールの引数や返される情報へ対応付けなければならない。

一つの作業システムで複数のプロセス記述やSkillを支えてよく、一つの記述やSkillを異なる構成で支えてもよい。共有する仕事の意味には共通の参照元となる記述を用いなければならない。実現を支える設計は、その目的と成果を独立して保持せず、参照元へ対応付けなければならない。実装上の選択では、適用される成果と条件を維持しなければならない。仕事の意味の変更には、フレームワークの変更原則を適用しなければならない。

根拠となる情報が十分であれば、どちらの設計責務から着手してもよい。作業システムの設計から、仕事の記述の再検討を要する前提が見つかることもある。[作業システムの設計Skill](../../../skills/design-agent-work-system/references/locales/ja/SKILL.md)自体もプロセス記述であり、その意味はフレームワークに従い、設計対象には作業システムの設計原則を適用する。

## 4. 基準となる記述、資源、実装

プロセス記述を記載する各Skillは、意味の基準となる記述を一つ識別できるようにしなければならない。翻訳、要約、リンク先の資料は、その記述との関係を明確にし、その意味と規範強度を維持しなければならない。

Skillは、必要な各付属資源の役割と利用条件を識別しなければならない。必要な参照は、意図した配布構成の下で利用可能でなければならない。パッケージ内の相対リンクは、その構成の下で解決しなければならない。外部参照は、意図した出典を識別し、アクセス条件がある場合はそれも明示しなければならない。必要な参照を確認できない場合は、フレームワークの規則を適用する。

`SKILL.md`と必要な参照資料は、仕事、判断基準、適用条件、必要なツールの利用方法を、利用する箇所で確認できるようにしなければならない。既存のCLIやAPIを直接利用してよい。Skillへの同梱が必要な処理は、そのSkillの`scripts/`へ配置し、[Agent Skillsのスクリプト作成ガイド](https://agentskills.io/skill-creation/using-scripts)に従って説明しなければならない。ツールの責務、呼出し方、引数と返される情報、依存関係、失敗への対応、状態を変更する影響は、作業システムの設計原則が求めるとおり記述しなければならない。

対象業務を遂行する同梱スクリプトは、対象Skillに置く。設計Skillに含めるスクリプトは、そのSkillが記述する設計や評価の仕事を支援しなければならない。実現を支えるシステムの実装と評価は、依頼範囲内に収めなければならない。対象業務の実行は、それ自体の適用条件を持つ別の適用である。

## 5. 評価

評価では、プロセス記述の意味上の妥当性、ツールと接続が仕様を満たすこと、代表的な適用における作業システムの有効性を区別しなければならない。各判断について、適用される基準、証拠、未実施の検証、限界を識別する。成果の判断にはフレームワークを、構成と相互作用の評価には作業システムの原則を適用する。

Agent SkillとPluginの形式検証では、形式、発見情報の整合性、参照元の識別、資源の利用可能性を評価する。それらは配布と利用に関する証拠を提供し、意味レビューと代表的な仕事は意味と有効性を評価する。
