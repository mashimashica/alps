# Process Framework

> “Or, paraphrasing, pragmatism identifies meaning with formation of a habit,
> or way of acting having the greatest generality possible, or the widest range
> of application to particulars.”
>
> — John Dewey, “The Pragmatism of Peirce” (1916), p. 711.

## Purpose and Authority

Work can take different forms as it moves from one context to another. Reuse depends on keeping its intent and boundaries legible without fixing the performer or method.

This Framework establishes a common, reusable basis for describing and understanding a Process—its intent, boundaries, work content, context, relationships, and evaluation—without binding the Process to one performer, tool, or execution pattern.

The Framework applies across application domains. It supports Process description, application, assessment, and improvement without prescribing one life cycle or method.

ALPS applies this Framework to Agent Skills. If an ALPS provision conflicts with this Framework, this Framework must take precedence.

In this Framework, **must** states a requirement and **must not** states a prohibition. **Should** states a recommendation and **should not** states a recommendation against an action. **May** states permission. Wording such as **typically** describes customary practice without creating a requirement. **Can** and **could** express possibility or capability and carry no normative attribute. Uppercase forms of these words are not used.

This Framework is the authoritative source for the meaning of these words. A specification or description that applies this Framework inherits those meanings and does not redefine them.

Examples, notes, conventions, diagnostic questions, and other reference information are informative. They must not change the meaning or normative force of the primary Process elements.

## 1. Work and Its Description

The first distinction is between work and the account of that work. One is performed; the other makes the performance understandable across contexts.

### 1.1 Work, Description, and Application

A **Process** is related work performed under a stated Purpose to establish one or more Outcomes. It acts on Inputs, produces Outputs, and brings Activities and Tasks into a coherent whole. Performing a Process is intended to provide benefits to stakeholders. The function of the Process is defined by its Purpose, Outcomes, and set of Activities and Tasks.

A **Process Description** explains a Process. The description is not the performance itself. It can represent a general Process or a particular Instance.

A **Process Instance** is one application of a Process in a particular context. An Instance-specific description can identify needed capabilities and resources, required incoming and outgoing items, applicable Controls and Constraints, and relevant timing.

### 1.2 The Description's Necessary Core

A description can grow in detail while retaining the same semantic center.

An explicit, systematic Process Description supports consistent results. A shared description structure also supports deployment of standard Processes, Tailoring, improvement, and Process Assessment and can be used with any Process Model regardless of domain.

Every Process Description must contain Name, Purpose, and Outcomes. These elements describe intended results without requiring structural decomposition and provide shared reference points for implementation and Assessment.

Activities, Tasks, Inputs, Outputs, Controls, Constraints, Enablers, Entry Criteria, Exit Criteria, and reference information are optional. They are included according to the Purpose of the description and the detail needed.

Processes can also be characterized by common attributes. The chosen detail can help characterize Process maturity, Capability, or quality.

### 1.3 Layers for Different Readers

Readers approach a Process for different reasons: to understand it, apply it, assess it, or improve it. Layers let each reader enter at the needed depth without dividing the Process into different meanings.

A common description form can use two parts: an overview and a detailed description. The overview can include Purpose, a description, Inputs and Outputs, Activities, Common Approach, practical tips, and summary good-practice information. Activities state what is performed; Common Approach and practical tips guide application.

The detailed part treats matters specific to the Process. Cross-cutting matters are treated separately from an individual Process's detailed description. This two-part presentation is optional and does not replace the required semantic core.

Overviews, descriptions, Common Approach, practical tips, notes, and examples are reference information that can support understanding or application of the Process.

### 1.4 Rules for Reading What Is Written

Order on the page is not order in execution, and fluent wording is not a substitute for distinct meaning.

A Process Description must keep the functions of Name, Purpose, Outcomes, Activities, and Tasks distinct and internally consistent.

Each sentence should carry one meaning. Independent objectives, results, or actions should not be joined merely to shorten the text. Each statement should include enough context to remain meaningful when referenced on its own. Supplementary explanation can be separated into a note or other reference information.

A general Process Description must not require a particular method, technique, tool, metric, management method, or execution sequence. Methods and examples can be offered as guidance without becoming Process requirements.

A Procedure prescribes ordered steps. Activities and Tasks describe Process work and must not be interpreted as procedural steps merely because they appear in an order.

Implicit timing, scheduling, and order should be avoided. A necessary temporal relationship should be stated explicitly as a Constraint. Without such a Constraint, no particular execution sequence is required.

Wording must distinguish requirements, recommendations, permissions, and typical actions so that their normative force is unambiguous.

## 2. Intent, Success, and Work Content

Language gives the work a recognizable shape before any Instance begins: the Name locates it, the Purpose explains why it exists, the Outcomes state what success establishes, and Activities and Tasks reveal what work belongs.

### 2.1 Naming the Work and Its Reason

A Name points to the work; a Purpose gives its reason. Keeping those functions apart prevents a label from carrying an objective it cannot explain.

The **Name** identifies the Process and distinguishes it from other Processes in the Process Model. A Name must be a concise noun phrase, must express the Process's central concern, and must not summarize the Purpose. In English, the word “process” should connect the Name; this is a language convention rather than a semantic requirement.

The **Purpose** must state the related high-level objective or objectives for performing the Process. It encompasses the Outcomes expected from effective implementation.

The Purpose should also clarify the Process boundary when neighboring Processes appear to overlap. It should be concise and, wherever possible, occupy one sentence. It should not summarize Activities or Outcomes or combine independent objectives. Supplementary explanation can be placed in reference information.

### 2.2 Distinguishing Success from What Is Produced

Success and production often travel together, but they answer different questions.

An **Outcome** is a measurable and tangible result condition achieved through the Process. It must be observable and assessable. It is not an Output, and merely creating a document, record, or information item must not be stated as an Outcome.

Each Outcome must establish one positive, observable condition in a declarative statement. An English Outcome must use a present-tense verb. Independent results must not be joined in one Outcome.

An Outcome of a general Process must remain meaningful throughout the Process's applicable scope. Together, all Outcomes must be sufficient for the Purpose, and every Outcome must be relevant to it. Each Outcome should also make sense when read separately.

Outcomes should be concise; a single clear meaning takes priority over brevity. The number of Outcomes follows from what the Purpose needs rather than from a fixed count. Benefits should be distinguished from Outcomes. When useful, an informative note associated with the Purpose can explain them.

An **Output** is what a Process produces as a product, result, or service. Outputs and Outcomes can be related, but they are not interchangeable: an Output is produced, while an Outcome is the result condition whose achievement is assessed. An Output of one Process can become an Input to another Process.

As a diagnostic question, ask whether the statement names an item that leaves the work or a condition used to judge success. The former indicates an Output; the latter indicates an Outcome. This test helps apply the definitions but does not replace them.

### 2.3 Grouping and Stating the Work

Work becomes intelligible when individual actions are gathered without losing their contribution to the whole.

An **Activity** is a cohesive set of Tasks within a Process. It organizes related actions so that their contribution to the Process can be understood and communicated.

A sufficiently cohesive and detailed Activity can be treated as a Sub-process with its own Purpose and Outcomes. Taken together, the Activities and any Sub-processes must cover every Process Outcome and satisfy the Process Purpose. Activities need not map one-to-one to Outcomes.

Tasks within an Activity should relate more closely to each other than to Tasks outside that Activity. An Activity must be treated as a continuous or iterative function narrower than the Process as a whole. The Activity set should address all Outcomes, but it may extend beyond the minimum work needed to satisfy the Purpose.

A **Task** states an individual action intended to support one or more Outcomes. Each Task must make clear whether the action is required, recommended, permissible, or typical. The Tasks assigned to an Activity need not enumerate every possible action within the Activity's boundary.

The timing and sequence rules in 1.4 apply to both Activities and Tasks.

## 3. Drawing the Process Boundary

A useful boundary is neither arbitrary nor a wall. It gathers work that belongs together and leaves its exchanges with other Processes visible.

### 3.1 Granularity and Cohesion

Process, Sub-process, and Activity do not have universal size boundaries. A significant Activity with many Tasks can be described as a Process when separate treatment is useful.

Primary Outputs and Outcomes typically provide the boundary test. Intermediate Activity Outputs do not usually determine the Process boundary.

Closely connected automated work that needs little human intervention can share one Process Description. Decomposition is useful while it improves understanding of boundaries, responsibilities, or relationships. An additional level that would harm understanding or use is omitted.

Within the boundary, Outcomes, Activities, and Tasks form a coherent explanation of why the work belongs together. Dependencies on other Processes are reduced as far as practicable.

### 3.2 What a General Process Leaves Open

Generality is preserved not by leaving the work vague, but by describing its function without assigning it to one performer or implementation.

A general Process does not prescribe the structure of the performer or who performs any part of the work. It describes the functional relationship needed for performance.

When applying a Process, Processes, Activities, and Tasks can be selected according to the Purpose. One Process or a combination of Processes can be performed.

The open choice of performer and implementation method is part of a general Process's reusability. It does not make the Process boundary incomplete.

## 4. What Crosses, Directs, Bounds, or Supports the Boundary

Once the boundary is drawn, each surrounding element can be understood by the role it plays at that boundary.

### 4.1 Classifying Elements by Function

Inputs and Outputs express connections between a Process and its external environment. They are used according to the Purpose of the Process Description and the detail needed.

An **Input** is an item that the Process transforms into an Output. It can come from another Process, an available information source, or a source outside the Process. Specifying required or representative Inputs is optional.

People, Agents, automation, tools, and execution environments used to perform the Process are resources rather than Inputs. When represented in a Process Description, they are Enablers.

A **Control** directs Process execution or the basis on which it is judged. Controls can arise from applicable laws or regulatory requirements, policies, conformance to voluntary standards, or agreements.

A **Constraint** limits the permitted execution of a Process. Constraints can arise from the environment or from conditions of application outside the Process.

An **Enabler** supplies capability that makes execution possible or supports it. Relevant capabilities, specialized capabilities, tools, and technologies are Enablers.

The same kind of artifact or information can serve different functions in different Processes. Classify each occurrence by asking what it does in that Process:

| Function in the Process | Classification |
|---|---|
| The Process changes it into an Output. | Input |
| It directs execution or the basis for judgment. | Control |
| It limits what execution is permitted. | Constraint |
| It makes execution possible or assists it. | Enabler |

Controls and Constraints can have their own sections or appear as notes to other Process elements.

### 4.2 Explaining Transformation Without Prescribing a Method

A transformation explanation tells a compact story: something enters, work acts on it, and something leaves. Controls, Constraints, and Enablers shape that story without becoming the item transformed.

Outputs are optional when Outcome achievement can be demonstrated. They can include items needed in a final product or service, intermediate work products used for validation or audit, and assets reusable by other products or Processes. The principal Output kinds are artifacts and information items.

A representative transformation explanation relates Inputs, Activities, and Outputs. Activities transform the Inputs; Enablers support that transformation; Controls direct or constrain its execution.

Results from a group of Processes are often recorded in documents, artifacts, or models. Naming an Output does not by itself require creation of a document.

Representative Inputs and Outputs show one possible manner of performance. They do not prescribe the only manner. A Process should be understood from the complete Process Description rather than only from its representative flow.

### 4.3 Conditions at the Edges of an Application

Beginning and completion are marked by conditions, not merely positions in time.

**Entry Criteria** state the conditions under which a Process can begin. **Exit Criteria** state the conditions under which it can be completed. When Entry Criteria and Exit Criteria are needed for the Purpose of a Process Description and its required level of detail, they should be included together with relevant Inputs and Outputs.

### 4.4 Handoffs and Traceability

A Process need not stand alone. Its Outputs can become another Process's Inputs, and Traceability keeps those relationships visible.

Traceability should cover Outcomes, Activities, Tasks, and information items. It shows consistency among Process elements. This evidence can also inform the design of tools used for Process Assessment.

Useful mappings include Tasks to Outcomes, Inputs to Outcomes, and Outputs to Outcomes.

A handoff between Processes maps a provider's Output to a recipient's Input. Making the direction and content explicit allows connections and dependencies to be understood. A handoff not defined beforehand can be added through Tailoring.

### 4.5 Elements Shared Across a Framework

Shared elements can keep a Framework coherent, but only when their reach is declared rather than assumed.

A Framework-level Control directs or constrains Processes within its declared scope. A Framework-level Enabler supports Processes within its declared scope.

For every shared Control or Enabler, its scope, exceptions, and permission for Tailoring must be stated. Mere membership in a Framework does not make a shared element applicable to every Process.

Controls or Enablers common to a declared scope may be stated once instead of repeated in each Process Description.

Examples of shared Controls include applicable laws, standards, agreements, application policies, directives, and governance requirements.

## 5. Reuse Without Freezing an Implementation

Reuse asks a description to hold a steady meaning while allowing different arrangements around it.

### 5.1 Frameworks, Models, and Reference Models

These constructs differ by the role they play:

| Construct | Role |
|---|---|
| **Process Model** | A Framework of interrelated Processes, which can be composed from multiple Processes. |
| **Process Reference Model** | A definition of individual Processes by their Purposes and Outcomes, with their relationships placed in an explicit structure. |
| **Process Framework** | A Process set and terminology for an application domain, used to compose Process Models and select Process subsets according to Purpose. |

A Process Framework can establish a desired Process environment, support selection and composition within an established environment, and provide a basis for agreement about Processes and Activities. It can be used to compose life cycle models. For Assessment, it can also function as the Process Reference Model. This Framework supports both Process Assessment and improvement.

### 5.2 Life Cycle Models and Changing Context

A life cycle model gives Process relationships an order for a chosen application; the document that describes them does not thereby turn its own clause order into time.

A **life cycle model** brings life cycle Processes and Activities into a shared basis for communication and understanding. Its details are expressed through the Processes, their Outcomes, their relationships, and their ordering.

The purpose of the application and the selected life cycle model determine actual Process order. The order of clauses in a document does not prescribe execution order.

Process selection and timing need continual review when the subject or context changes. Process use can change dynamically in response to internal or external influences.

### 5.3 Process Views

A View changes the angle of attention, not the source Process Model.

A **Process View** organizes Activities and Tasks from multiple Processes around a concern or Purpose and explains how its Outcomes are achieved. It makes cross-cutting concepts or a particular Purpose visible.

Every Process View must state its Name, Purpose, and Outcomes. It must provide explanation and guidance for applying the included Activities and Tasks.

A Process View may contain Activities and Tasks with any of the following origins:

| Origin in the View | Required treatment |
|---|---|
| Selected from a Process Model | Identify the source, label the element as selected, and retain the source. |
| Adapted from a Process Model | Identify the source and label the element as adapted. The adaptation does not change the source Process Model. |
| Created specifically for the View | Label the element as new. The View-specific element does not change the source Process Model. |

The View must identify the source of each Activity and Task and label it as selected, adapted, or new. Adapted and View-specific elements do not contribute to Conformance with a source Process unless Tailoring or formal adoption incorporates them into that Process.

A Process Framework may restrict a Process View to Activities and Tasks already present in a Process Model. A restricted View must not include View-specific Activities or Tasks.

A Process View may also show connections among Processes and the sources of the Processes used in its composition.

## 6. Connecting and Reapplying Processes

Processes need not advance along a single line. They can share a level, return at that level, recur at another level, and be integrated across the resulting structure.

### 6.1 Four Independent Relationships

The following terms answer different structural questions and can be combined:

| Relationship | What changes or is coordinated |
|---|---|
| **Concurrency** | At least two Processes are applied in parallel at the same structural level. |
| **Iteration** | A Process or Process set is reapplied without changing structural level, including repeated interaction among Processes. |
| **Recursion** | A Process or Process set is reapplied at successive structural levels of the subject of application. |
| **Integration** | Completeness is established within one level and consistency between levels. |

Iteration returns without changing level; Recursion repeats a Process or Process set across structural levels. Concurrency concerns coexistence, while Integration concerns completeness and consistency.

Process execution is not limited to a serial arrangement. Iteration progressively refines Outputs, incorporates decisions and evolving understanding, addresses Constraints, and resolves trade-offs. Iteration is expected, not merely allowed. It should continue until the problems arising from the Processes are resolved.

In Recursion, an Output at one level can become an Input to a Process at the next level.

### 6.2 Flow and Change Propagation

Concurrency, Iteration, and Recursion do not imply timing or sequence. The actual flow must be determined through Tailoring according to application needs.

When Iteration or Recursion changes an Output, Inputs to affected Processes change as well.

## 7. From a General Process to One Application

A general Process becomes concrete in two different ways: its applicable form can be tailored, and one application can be instantiated. The two can occur together, but they do not name the same change.

### 7.1 Adaptation and Rigor

**Tailoring** is the controlled Adaptation of a life cycle model or Process to the needs and conditions of a declared context. Such models and Processes typically cannot be applied unchanged in every context.

Tailoring sets enough rigor for Activities to be performed at an acceptable level of risk. Too little rigor raises the chance of problems; too much can raise cost or schedule risk.

Tailoring typically continues dynamically throughout application as risk and context change. Its operation should be reviewed and revised when conditions warrant.

### 7.2 What Tailoring Can Change

**Common-level Tailoring** adapts an external standard to needs shared across an intended application domain.

**Individual-level Tailoring** adapts the resulting common Process to one subject of application.

Tailoring can delete, modify, or add Outcomes, Activities, Tasks, representative Inputs, and representative Outputs.

### 7.3 Establishing a Tailoring Decision

Context is lost when an earlier answer is treated as universal. Tailoring keeps its assumptions, evidence, scope, and criteria in view.

Tailoring must identify application risks, requirements, complexity, available capabilities and resources, and relevant standards.

Candidate Processes or life cycle models must be evaluated using the conditions of application, available expertise and experience, stakeholder expectations or requirements, and risk tolerance.

Tailoring must obtain Input from affected parties and must comply with applicable Controls and Constraints.

Tailoring decisions should rest on facts and evidence. The scope should be explicit. Assumptions and criteria should be identified. The rationale for selecting a Process or life cycle model should be recorded and maintained.

A means of continually assessing the tailored Process should be established.

Tailoring has pitfalls that erase the declared context. Representative pitfalls include carrying forward another subject's tailored baseline without applying Tailoring again, including every Process and Activity merely as a precaution, treating one measure, risk, or Control as universal, applying a pre-established tailored baseline unchanged, or excluding affected stakeholders.

### 7.4 Process Instantiation

When quality risk justifies the detail, **Process Instantiation** describes a Process Instance for a particular subject and context.

Instantiation derives Instance-specific success criteria from requirements and identifies the Activities and Tasks that will achieve them. The resulting links between the Process and particular requirements support management of quality risk.

Tailoring changes the Process or life cycle model that is applicable. Instantiation describes one application of the applicable Process in greater detail. This distinction does not prevent a tailored Process from being instantiated.

## 8. Evidence, Decisions, and Claims

Evidence connects work to judgment. It makes a Gate decision reviewable and a Conformance claim examinable.

### 8.1 Decision Gates

A Gate marks a judgment without becoming a stage in the Process Description.

A **Decision Gate** is a decision mechanism that controls Process application; it is not a component of a Process Description.

At a Decision Gate, Decision Criteria determine whether the uncertainty and risk of proceeding to a later Activity or changing Process state are acceptable. The Purpose, Outcomes, conditions of application, and risk assessment can supply those criteria.

Gate frequency, scope, and formality can be adjusted to the context. More frequent gates can use narrower scope and less formality.

A Gate decision should be explicit and recorded. Available decisions can include continue, hold, change, re-execute, or terminate. The quality of current results and the risk of proceeding inform the choice.

Before a Gate, a review should use the necessary expertise and relevant Inputs. Passage should rest on evidence that the Decision Criteria are met. Criteria should be updated and reevaluated at each Gate as the context changes.

An Output accepted at a Gate can become a basis for later Activities. The decision, rationale, and assumptions should be recorded and placed under the change management needed for the context.

### 8.2 Reviews and Audits

Review asks how the work and its results stand against agreed criteria; audit asks what the evidence establishes about Conformance.

A **review** evaluates Process performance, Outputs, and Outcome achievement against agreed criteria.

An **audit** examines evidence of Conformance to Processes, Outputs, and requirements in detail. It confirms whether mandatory attributes and applicable requirements are satisfied.

Reviews and audits should appear in the application plan and be tailored to the subject and methods. Good practice gives them unambiguous starting and completion conditions and triggers them by risk or events rather than schedule alone.

It is good practice to make preparation, conduct, and acceptance methods and conditions clear and to include the necessary expertise and an independent perspective. When a problem is detected, it is also good practice to establish a clear action with a due date and completion conditions and to track it.

### 8.3 Full Conformance Claims

A Conformance claim says more than that a Process was followed. Its selected basis identifies the conditions it demonstrates.

Full Conformance to a Process must be claimed as Outcome Conformance, Task Conformance, or both. A Conformance claim must identify the selected basis. When both bases are claimed, both sets of conditions must be satisfied.

The two bases answer different questions and can impose different obligations:

| Basis | Condition for Full Conformance | Status of the other elements |
|---|---|---|
| **Outcome Conformance** | Every mandatory Outcome in the declared Process is achieved. | Activities and Tasks are guidance, allowing freedom in implementation. |
| **Task Conformance** | Every requirement stated with **must** or **must not** in the Activities and Tasks of the declared Process is satisfied. | Outcomes are guidance. Recommendations, permissions, and typical actions do not become mandatory merely from their presence. |

Outcomes can be achieved and Activities or Tasks can be performed beyond what a Conformance claim requires.

### 8.4 Tailored Conformance Claims

**Tailored Conformance** may be claimed when a Process set does not satisfy the selected Full Conformance basis.

The claim must identify the Process or Processes tailored through the Tailoring Process and declare the application scope. It must demonstrate satisfaction of the Outcomes that remain in scope and of the requirements in the Activities and Tasks that remain in scope.

### 8.5 Capability and Process Assessment

Capability and Conformance are separate assessment dimensions. Performing specified Activities and Tasks can require a higher Capability level than achieving Outcomes alone. Capability does not by itself establish Conformance, and Conformance does not by itself determine Capability.

Process Outcomes can be used as the Process Reference Model in Assessment and improvement. Process Purposes and Outcomes state implementation objectives, enabling effectiveness to be assessed by means other than simple conformity assessment.

## 9. Keeping Processes Useful

Experience returns to a Process through measures, lessons, comparison, and change.

### 9.1 Management and Application

Process management should define how Processes are governed and made available and should provide Tailoring guidance for individual applications.

It should establish indicators of Process effectiveness and efficiency and use those indicators to assess performance.

Applicable Processes should be identified. Their implementation and maintenance should be documented. Established supporting methods and techniques should be used, and Tailoring guidance should be applied to the specific need.

Changes in management guidance should be communicated to affected users. Improvement opportunities should be continually identified, prioritized, and implemented.

### 9.2 Standard Processes and Comparison

Consistent use of standard Processes across multiple subjects supports repeatable and predictable performance. It also allows proven practices and lessons to support later applications, helps new applications begin, and advances continued improvement.

Process benchmarking compares performance with declared criteria, applicable standards, or other comparators to find improvement opportunities. The comparison should address performance, effectiveness, Conformance, benefits, and costs.

### 9.3 Measures, Assessment, and Learning

Measures reveal patterns; lessons give those patterns context; improvement connects both to action.

Process strengths and weaknesses should be assessed, and reviews and audits should be established.

Measures should be established to provide insight into Process performance and effectiveness. Those measures should be analyzed to determine effectiveness.

Mechanisms should collect lessons learned, connect them to action, and analyze candidate Process changes.

Lessons should be collected throughout execution and at planned milestones. Lessons and measures should be reviewed periodically to improve Processes and practices.
